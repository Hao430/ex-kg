# DeepDive 开发规范

> **版本**：v1.0.0
> **适用范围**：本仓库全部代码、文档与协作流程
> **原则**：约定与现有代码库保持一致；新增代码必须遵守本规范，存量代码在触碰时逐步对齐

---

## 1. 命名规范

### 1.1 文件与目录

| 对象 | 规则 | 示例 |
| :--- | :--- | :--- |
| 服务端目录 | 全小写复数/单数分层名 | `server/core`、`server/repositories`、`server/services`、`server/middleware`、`server/routes`、`server/lib`、`server/jobs` |
| 服务端文件 | camelCase，按 `领域.职责.ts` 命名 | `user.repository.ts`、`billing.service.ts`、`auth.ts`（中间件与库为纯单词） |
| 前端组件文件 | PascalCase | `RechargeModal.tsx`、`AdminDashboardModal.tsx` |
| 前端非组件文件 | camelCase | `storage.ts`、`sync-queue.ts`（既有连字符保留） |
| 测试文件 | `<spec编号或主题>-<主题>.test.ts` | `b1-quota.test.ts`、`f5-f6-crypto-cleanup.test.ts` |
| 文档 | 中文标题命名；spec 文档以里程碑编号开头 | `docs/需求说明文档.md`、`docs/specs/B1-配额服务端化.md` |
| 环境变量 | 全大写 SCREAMING_SNAKE | `DATABASE_URL`、`AI_LOG_RETENTION_DAYS` |

### 1.2 标识符

| 对象 | 规则 | 示例 |
| :--- | :--- | :--- |
| 函数 / 变量 | camelCase，动词开头 | `findUserById`、`saveBoard`、`assertCanCreateBoard` |
| 类型 / 接口 | PascalCase，数据记录以 `Record` 结尾 | `UserRecord`、`CanvasRecord`、`StoredBoard` |
| React 组件 | PascalCase | `const Topbar: React.FC<TopbarProps>` |
| 常量 | 全大写 SCREAMING_SNAKE | `MAX_RETRIES`、`BOARD_LIMIT`、`GRACE_PERIOD_DAYS` |
| 数据库表 / 列 | 全小写 snake_case | `user_audit_logs`、`vip_expires_at`、`canvas_id` |
| API 路径 | 复数资源名 kebab-case 子资源 | `/api/canvases/:id/save`、`/api/admin/audit-logs` |
| 错误码 | 全大写 SCREAMING_SNAKE | `BOARD_LIMIT_REACHED`、`MODEL_VIP_ONLY` |
| 审计 action | 全小写 snake_case 动词短语 | `sign_in_failed`、`canvas_delete`、`vip_grant` |
| Git 分支 | `feat/<主题>`、`fix/<主题>` | `feat/quota-middleware` |

## 2. 提交规范

采用 **Conventional Commits**：`<type>(<scope>): <subject>`

### 2.1 type 取值

| type | 用途 |
| :--- | :--- |
| `feat` | 新功能（含里程碑工作项落地） |
| `fix` | 缺陷修复 |
| `refactor` | 重构（行为不变或行为变更已在正文说明） |
| `perf` | 性能优化 |
| `test` | 仅测试变动 |
| `docs` | 仅文档变动 |
| `chore` | 构建、依赖、杂项 |

### 2.2 规则

1. **一次提交对应一个验收通过的功能点**（spec → 测试 → 实现 → 审计通过后才提交）
2. subject 用中文简述；正文列出关键改动点与验收依据（spec/tests 路径）
3. scope 使用里程碑编号或模块名：`feat(B1): ...`、`refactor(C): ...`
4. 禁止提交：`node_modules`、`dist`、`.env`（真实密钥）、运行时锁文件
5. 提交前必须通过：`npx tsc --noEmit` + `npm test` 全绿

## 3. 代码规范

### 3.1 TypeScript

- `strict` 模式；禁止 `any` 逃逸到公共 API（边界解析数据允许 `as any` 并注明原因）
- ESM（`type: module`）：**相对导入必须带 `.js` 后缀**（`from './core/pool.js'`）
- 公共函数必须有显式返回类型（`Promise<UserRecord | null>`）

### 3.2 分层与依赖方向（严格单向）

```
routes → services → repositories → core
                    ↘ lib（纯工具）
```

- `routes`：zod 校验 + 调 service + 组装响应；**禁止** SQL / 内存 store / 业务规则
- `services`：业务规则与编排；**禁止** 直接 SQL；抛业务错误（`AppError` 子类）
- `repositories`：数据访问 + PG/内存双模分支；**禁止** HTTP 概念（req/res）
- `core`：连接池、schema 迁移、内存兜底存储、记录类型
- `middleware`：鉴权 / 限流 / 统一错误处理

### 3.3 错误处理

- 业务错误一律抛 `server/lib/errors.ts` 中的 `AppError` 子类，携带 `code`
- 路由 async handler 必须用 `asyncHandler()` 包裹（Express 4 不捕获 async 异常）
- 请求体校验用 `validate(schema, body, code?)`，失败统一 400 `VALIDATION_ERROR`
- repository 层 PG 失败 → `console.warn` + 内存兜底（双模容灾）；**事务类操作失败必须抛出**（如 `saveCanvas` 批量保存）
- 副作用（审计、日志）失败不得阻塞主流程

### 3.4 双模持久化

- 所有读写函数同时覆盖 PG 与内存两条路径，内存为降级兜底
- **禁止双写**：PG 成功时不写内存；内存仅在无 pool 或 PG 失败时兜底（清理型操作如删除会话除外）
- 事务：`BEGIN`…`COMMIT`，catch 中 `ROLLBACK` 后重新抛出

### 3.5 安全

- 新增入参必须有 zod schema；新端点必须确认鉴权中间件与所需角色
- 涉及权限/订阅/删除/配置变更的操作必须写 `user_audit_logs`（`recordAuditLog`）
- 密码一律 `hashPassword`（scrypt 加固参数 + 版本头）；禁止明文/自定义散列
- 限流：新增公开端点（**含匿名读**，如访问计数、公开查询）必须评估是否需要 IP/用户级限流

## 4. 注释规范

1. **写为什么，不写是什么**——代码自解释的部分不加注释
2. 公共导出函数用 JSDoc（一句话职责 + 关键参数/异常）；私有实现仅标注非直观逻辑
3. 业务规则注释引用 spec 编号：`// Spec B1：新建画板前校验画板数配额`
4. 临时妥协 / 演示数据用统一格式：`// TODO(<编号>): <说明>`（如 `TODO(A3)`）
5. 删除代码时一并删除其注释；禁止保留注释掉的死代码
6. 语言：注释与文档统一中文；标识符英文

## 5. 结构规范

### 5.1 服务端目录职责

```
server/
├── server.ts        # 入口：env、启动、监听、Vite/静态资源（路由与中间件不在此挂载）
├── app.ts           # createApp() 工厂：中间件与全部路由统一挂载于此（集成测试实例化用）
├── core/            # 基础设施：pool、schema 建表迁移、memory-store、records 类型、db-status
├── repositories/    # 数据访问 + 双模分支（每个领域一个文件）
├── services/        # 业务编排（auth/billing/ai/canvas/admin/quota/feedback）
├── payment/         # （services/payment）支付渠道抽象与实现
├── middleware/      # auth（鉴权/限流）、quota（推理配额）、error-handler
├── routes/          # HTTP 端点定义
├── jobs/            # 后台任务（log-cleanup）
└── lib/             # 纯工具：crypto、errors、async-handler、validate、mailer
```

- **新路由一律挂载在 `server/app.ts` 的 `createApp()` 中**，禁止直接挂在 server.ts（绕过工厂会导致集成测试覆盖不到）
- 新领域 = 新增 `X.repository.ts` +（可选）`X.service.ts`；禁止跨领域直接 import 另一领域的私有函数
- 跨领域编排走 service（如订阅激活同时触达 user 与 order）

### 5.2 文档结构

```
docs/
├── 需求说明文档.md        # PRD
├── 技术架构文档.md        # 架构与数据模型（与代码同步维护）
├── 里程碑与分期规划.md     # 唯一进度事实源（工作项完成即更新勾选状态）
├── 数据库建表脚本.sql
├── specs/                # 每个 spec 一份：<编号>-<主题>.md（改动前编写）
└── 开发规范.md           # 本文档
```

- spec 模板：来源 → 设计 → 测试先行 → 验收标准（可勾选）
- 文档与代码冲突时：以里程碑决策为准修文档（G 组模式），不允许文档口径漂移

### 5.3 前端结构

```
src/
├── components/   # UI 组件（按域分子目录：admin/auth/canvas/landing/nodes/ui）
├── context/      # 全局状态（AuthContext）
├── hooks/        # 自定义 Hooks
├── lib/          # 工具与 API 客户端（storage/sync-queue）
└── types.ts      # 前端类型契约（与后端响应形状隐式对齐）
```

## 6. 测试规范

1. **测试先行**：spec 落地前先写测试并确认 RED；实现后 GREEN
2. 框架：`node:test` + `tsx --test`（`npm test`）；断言用 `node:assert/strict`
3. 集成测试模式：`createApp()` + 随机端口 + fetch；种子等待轮询 `/api/db/status`（不用登录接口，避开限流）
4. 用例必须确定性：禁用真实时间断言（边界用例改注入基准/手动驱动），禁用跨用例共享计数
5. 每个里程碑工作项至少覆盖：正常路径 + 越权（403）+ 不存在（404）+ 配额/校验拒绝（400/403）
6. **注意限流预算**：`signupRateLimiter` 为 5 次/小时/IP——涉及密集注册断言的用例会触发 429（先例：d1 套件第 6 次注册即 429），必要时注入独立限流实例或复用已注册账号
7. 验收前全量跑 2 次确认无 flake

## 7. 里程碑开发流程（spec 规范）

每轮开发固定七步：

```
1. 认领工作项（docs/里程碑与分期规划.md，按 A→B→C…顺序）
2. 写 spec：docs/specs/<编号>-<主题>.md（来源/设计/测试先行/验收标准）
3. 写测试（RED）
4. 实现（可分配子代理；约束与验收标准写入任务）
5. 子代理代码审计（通过 / 修复后通过）
6. 更新里程碑勾选状态
7. git 提交（Conventional Commits）并续排下一轮
```

## 8. 版本与环境

- 运行时：Node.js ≥ 24（`tsx` 直跑 TS）；包管理 npm，唯一锁文件 package-lock.json（bun.lock 已移除，禁止重新引入第二把锁）
- 脚本：`npm run dev` / `build` / `start` / `test` / `lint`
- 敏感配置只进 `.env`（`.env.example` 同步维护占位与说明）
- 数据库结构变更一律写进 `server/core/schema.ts` 的幂等迁移（`ADD COLUMN IF NOT EXISTS` / `DROP ... IF EXISTS`），禁止手改线上库
