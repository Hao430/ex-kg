## Context and Problem Statement

画布同步长期是 **local-first 双模**（ADR-0002 / ADR-0008）：本地 blob 与 localStorage
索引是真相源之一，上行是**整板替换**，409 冲突时「本地版胜出」（刷新版本号后原样重发）。

线上反复出现同一类投诉：**「半天没上传，改完被云端的覆盖掉了」**。机理是两处相乘：

1. 服务端每次保存都是整板替换（`DELETE FROM nodes WHERE canvas_id = $1` 后全量重插），
   节点没有独立版本；
2. 客户端遇到 409 的策略是**本地版覆盖服务端**——乐观锁被用来「重试」，从没被用来
   「保护」。

结果：**赢的是「最后同步的那台设备」，不是「最后编辑的那份内容」**。挂机半天没传上去的
设备一旦恢复，会把它的旧快照整板覆盖上去，另一台设备这期间的改动一次性消失。

讨论是从另一个方向进来的：**「要不要上长连接 / 云原生创作」**。结论是长连接不解决问题——
它改变的是「谁先开口」与推送延迟，不改变同步的难点；冲突合并、离线编辑、幂等重放、删除
与复活、乱序到达，在 WebSocket 上一个都不会消失，还会多出「断线重连后如何重新对账」这
一层状态。**socket + LWW 只会把冲突从「保存时」提前到「编辑时」，冲突数量一个不少。**

## Decision Drivers

- **数据不丢 > 离线可用**：被覆盖的是用户二十分钟的思考内容，离线可用是便利性；
- **产品拍板：用户可以接受无网不可用**（2026-09-11）——离线可编辑不是必须保的能力；
- 拓扑约束：单机 pg-host、1.6G 内存红线、宝塔 Node 管理器、rsync + `kill` 后重启
  （2–4s 中断）。长连接意味着每连接常驻内存、**每次发版全部断线**、nginx 与面板都要
  额外配 upgrade 与超时，将来多实例还得引入 pub/sub；
- **「无本地状态」与「不卡」不可兼得**：每次编辑等服务端确认 = 用户报的「感觉慢/卡」；
  乐观 UI 先行 = 本地立刻就有未确认状态，冲突窗口原封不动回来，只是变短。乐观 UI
  就是本地状态；
- 不引入 CRDT/Yjs 级依赖（与 ADR-0008 的取舍一致）。

## Considered Options

- **Option A: 长连接（WebSocket / SSE）推送，状态模型不变** — 只解决「服务端主动推」
  这一类需求（多人同屏、别人的改动我要立刻看到、在线状态）。是传输层优化，不是状态
  模型变更。
- **Option B: 服务端权威（cloud-authoritative）+ 节点级合并 + 墓碑**（已选） — 本地从
  **真相源**降级为**未确认缓冲**；服务端定序，冲突在架构层面消失。
- **Option C: 维持 local-first，只把冲突粒度从整板降到节点** — 保留离线能力，成本最小，
  但本地仍是真相源之一，「最后同步的赢」只是被缩小到节点粒度，不会被消除。

## Decision Outcome

**Chosen option: "B"**，因为在「无网不可用已被接受」的前提下，它把冲突从**架构层面**
消掉（压根不存在两份分叉的状态），而不是把冲突窗口缩短——后者只让故障从「常见且可复现」
变成「罕见且不可复现」，调试难度反而上升。

### 一条最容易漏的约束

**节点级合并是云优先的前置条件，不是它的替代品，也不是可以先跳过的部分。** 因为整板替换
**即使全程在线、零离线**也会丢改动：两台设备的两个请求只要一前一后到达，后到的整块板就
把前一块覆盖了。云优先只免掉「离线」那一个分支，不免掉合并本身——ADR-0017 先行的理由
就在这里。

### Positive Consequences

- 用户投诉的机理被消除：409 不再丢服务端那份，「最后编辑的赢」在**节点粒度**上成立；
- 列表真相收口到服务端快照（`board-store`），localStorage 索引降级为**绘制缓存**，
  不参与裁决；
- 顺带消掉一整层由 local-first 派生的复杂度来源（幽灵板判定、scope 隔离与旧键迁移、
  配额 pendingCreates、多账号下的列表缩水/假成功）。

### Negative Consequences

- **无网即不可编辑**（此前至少能打开继续写）——这是明确接受的产品代价；
- **单点故障从「降级」变成「全站停摆」**：服务端不可用时不再有本地兜底；
- 换了一组新复杂度：连接状态 UI、请求重排与幂等、跨设备可见性；
- **冲突不再自愈，需要一条安全网**：本地未同步版会被另存为「(冲突副本)」画板
  （`src/lib/storage.ts` 的 `preserveLocalAsConflictCopy`）。安全网本身也是要维护的代码。
  - 补记（2026-09-18，ADR-0025）：**该安全网已删除**。载入改为以服务端为准（本机未上行内容
    直接丢弃），不再有「本地版另存副本」这一步；理由见 ADR-0025「Considered Options」。

### Follow-up / Mitigation

- **冲突副本**：409 时先另存副本再采用服务端版，用户的改动不丢；同轮冲突复用同一块副本，
  源画板保存成功后清空复用表；
  - 补记（2026-09-18，ADR-0025）：**已作废**。冲突副本子系统整条删除，409 改为纯防御
    （`CLIENT_OUTDATED` → 停止重试并提示刷新）；载入采用服务端时本机未上行内容按设计丢弃；
- **SSE 而非 WebSocket**（若将来需要「多设备看到最新」）：单向推一个 `board-updated`
  事件、前端复用既有 stale-while-revalidate 重拉即可——无状态、单向、nginx 好配、
  部署断线自动重连。多人同屏才需要 socket + CRDT，那是另一个立项；
- **不再把长连接当止血带**：它会把「数据被覆盖」这个信号盖住。

### 安全网的首次真实考验（2026-09-14，未通过，已修）

事故：一块画板以 **60 秒间隔**连续 400 重试 20 分钟（19:39:56 → 19:59:12，29 次），
内容始终没落库。

根因：冲突副本只换了**画板 id**，节点/边的 id 原样保留。服务端 `nodes.id` 是全局主键，
`mergeWriteCanvas` 的跨板拦截（`canvas.repository.ts` 步骤 1）查到这些 id 已属于源画板即
整次拒收（`NODE_CANVAS_MISMATCH`）。**后果不是「保存慢」而是安全网失效**：副本永远传不
上去，只活在那台浏览器的 localStorage 里——换设备、清缓存，那些「已保住」的改动照样没了。
它恰好在唯一该起作用的那一刻失灵。

同一个坑此前已修过一次（`910acdd fix(M2): 分享克隆重映射 node id`），那次抽出了
`src/lib/board-remap.ts` 并写明「任何『把既有画板复制成新画板』的路径都必须重映射 id」，
唯独冲突副本这条复制路径没跟上。

已修（2026-09-14 三个提交）：副本改走 `remapBoardIds`；服务端确定性 4xx 不再转成无限
重试（新增 `SyncOutcome = 'rejected'`）；跨板拒收补上可定位的日志上下文。

**教训**：安全网要按「主路径」的标准写测试。原先 `tests/a6-conflict-self-heal.test.ts`
断言的正是这个 bug——`deepEqual(副本.nodes, [LOCAL_NODE])` 要求 id 相同，等于把 bug
写成了预期。测试写成什么样，bug 就长什么样。

> 补记（2026-09-18，ADR-0025）：这次修复只救回了副本的**可用性**（能上传），没有触碰副本的
> **触发条件**（假 `dirty` + 整板版本号比对）。触发条件随后继续制造「本机什么都没改也冒出
> 副本」与「异节点并发编辑却复制整块板」，直到 ADR-0025 把整条机制删除。

### 残留风险（明确接受）

1. **无网不可用**：已接受，但**尚未在 UI 口径上体现**——服务端不可用时用户看到的仍是
   泛化的「同步失败」，而不是「当前无网络连接，画板暂时不可编辑」。这是本决策引入的
   新缺口，待登记；
2. **单点故障**：服务端挂 = 全站停摆。1.6G 单机是既有前提，不在本决策范围内；
3. **同节点并发编辑**仍是最后到达者胜——影响面已缩到节点粒度，见 ADR-0017 残留风险；
4. **跨设备可见性**未做（需 SSE 或 focus 时比对版本），意味着「另一台改了、我这台还
   显示旧内容」仍会发生——但**不会再丢数据**：那台设备保存时 409 会把它引到副本路径。
   - 补记（2026-09-18，ADR-0025）：副本路径已删除，改为「载入即采用服务端」——仍然不会
     丢服务端的数据；本机那份未上行内容则按设计丢弃（见 ADR-0025 Negative Consequences）。

### 明确不做

- **CRDT / Yjs / Automerge**：产品是「个人多设备」而非「多人同时编辑」，收益不匹配成本；
- **阻塞等 RTT 的「服务端确认后才更新画面」**：直接等于用户报的「卡」；
- **WebSocket 长连接**：在单实例 + 发版即重启的拓扑下代价大于收益；将来真做多人同屏
  再立项（届时 socket 只是传输层，合并仍需 CRDT/OT）。

## Pros and Cons of the Options

### Option A: 长连接（状态模型不变）

- **Good**：感知更快；服务端可主动推；为将来的多人协作铺路
- **Bad**：冲突数量一个不少（只把窗口缩短）；每次发版全部断线需重连对账；单实例下
  进程内广播够用但锁死横向扩展；宝塔/nginx 均需额外配置

### Option B: 服务端权威 + 节点级合并 + 墓碑（已选）

- **Good**：冲突在架构层面消失；整层 local-first 复杂度可收；「最后编辑的赢」在节点
  粒度成立
- **Bad**：无网不可编辑；单点故障；仍需节点级合并（云优先不免掉它）

### Option C: 维持 local-first，只做节点级合并

- **Good**：保留离线能力；改动最小；成本最低
- **Bad**：本地仍是真相源之一，冲突只是被缩小而非消除；local-first 那整套复杂度
  （scope 迁移、幽灵板、配额 pendingCreates）继续背着
