# ADR-0026: 同一浏览器多标签采用单写者编辑锁

- **Status**: Accepted
- **Date**: 2026-09-18
- **Deciders**: 枝想架构组
- **Tags**: sync, concurrency, frontend, canvas

## Context and Problem Statement

ADR-0025 把「载入以服务端为准」定下来之后，同一块画板在**同一浏览器开两个标签页**仍会互相破坏。
根因是本地状态的共享方式与内存状态的所有权不匹配：

- 画板 blob（`deepdive_board_*`）、服务端版本小键、节点级差分基线（`deepdive_board_base_*`）
  与同步队列都是 **localStorage 共享、不按标签隔离**；
- 每个标签的 React 状态、`nodesRef`、画布实例则是**各自独立**的。

于是两条破坏路径同时成立：

1. **覆盖**：B 标签按自己内存里的整块板写 blob，把 A 标签刚保存的节点抹掉；
2. **误删（更严重）**：A 保存成功后推进了共享基线，B 随后按新基线做差分，会把自己
   「没见过」的节点判成本地删除 → 在服务端**真的删掉** A 的内容。

owner 反馈的实际现象正是「多设备/多标签页都改过同一块板」。ADR-0025 只解决载入时的裁决方向，
不解决标签之间的状态所有权，因此需要单独决策。

## Decision Drivers

- **不丢数据优先**：误删发生在服务端，比本地覆盖更严重；宁可明确不可编辑。
- **与既有取舍一致**：ADR-0021 已接受「无网即不可编辑」——为正确性牺牲可用性在本项目是既有口径。
- **不引入新状态模型**：CRDT/OT、跨标签合并都会把复杂度抬到「多人协作」量级，而产品是「个人多设备」。
- **观测与可解释**：用户必须看得懂「为什么这里不能编辑」，而不是遇到一个不响应的界面。

## Considered Options

- **Option A: 单写者编辑锁**（已选） — 同一画板任何时刻只允许一个标签持有编辑权，其余标签显示闸门。
- **Option B: 跨标签协调** — 保存时广播，其他标签收到后重新对齐或合并上传。
- **Option C: 按标签隔离存储** — blob/基线/队列改用 sessionStorage，两个标签退化成「两台设备」。
- **Option D: 只提示不改行为** — 检测到多标签就警告，但仍允许两边编辑。

## Decision Outcome

**Chosen option: "A"**，因为它是唯一能同时消掉「覆盖」与「误删」两条路径、且不引入新状态模型的方案。

- **B 被否**：要正确处理「本标签有未上传差分 + 他标签已推进基线」，必须把 ADR-0025 的
  「载入即采用」（丢弃本机未上传内容）与「保留本标签未上传内容」两条规则拼在一起，
  边界多、易错，收益只是「两个标签都能改」。
- **C 被否**：可行但代价是「关标签丢本地绘制缓存与未提交草稿」，且队列也得分标签，
  相当于把「多设备模型」搬到同一个浏览器里；用户得到的体验反而更差。
- **D 被否**：底层破坏机制原样保留，只是把风险从「静默」变成「已知」，不解决误删。

### 落地

- 模块：`src/lib/board-edit-lock.ts`（`createBoardEditLock` 工厂 + `getBoardEditLock` 单例），
  基于 `BroadcastChannel`，单频道 + 按 `boardId` 过滤。
- 协议：
  - 进入画板发 `claim`；**tabId 字典序小者胜**，双方按同一规则各自收敛，无需协商；
  - 持有者按 `heartbeatMs`（2s）广播心跳；非持有者 `leaseMs`（5s）内没收到任何对方消息
    即认为对方标签已被系统杀掉（这种情况没有 `release` 可发），自行接管；
  - 用户点「在此标签页继续编辑」→ 发 `force` claim，持有者**无条件让出**（这是用户意图，不比 tabId）；
  - 收到 `release` 且当前无主 → 立即 `claim`，避免出现「两个标签都只读」的空档；
  - `release()` **先清本地状态再广播**：对方收到 release 会立刻 claim 并同步回投给我，
    若此刻我仍认为自己持有就会重申 claim 把对方刚拿到的锁打掉（这条正是被单测逼出来的 bug）。
- 应用侧：非持有者**不渲染编辑画布**，改为 `BoardLockedNotice`（说明 + 「在此标签页继续编辑」+
  「打开画板库」）；破坏性操作（清空画板、删除当前画板、导入备份、关闭灵感占位、重命名当前画板）
  在非持有者上一律拒绝并提示；`handleCanvasChange` 亦加守卫兜底。
- **接管前必须先按服务端对齐**（`fetchBoardFromServer` → 采用后再拿锁）：上一个编辑者可能刚把
  改动传上去，我们手里的画面与基线是旧的；顺序反了，中间那一次防抖保存会把对方的节点当成本地删除。
- 环境缺 `BroadcastChannel`（老浏览器/测试）→ 退化为「永远持有」并保持可编辑：**不能因为抢不到锁
  就把用户挡在外面**。

### Positive Consequences

- 两条破坏路径（覆盖、误删）同时消除；标签之间不再共享写权限。
- 决策面小、可单测：协议不变量（至多一个持有者）由 `tests/board-edit-lock.test.ts` 锁定。
- 与 ADR-0025 的语义相容：非持有者让出前先 flush 待发改动，不会因为切到闸门而丢内存里的编辑。

### Negative Consequences

- **第二个标签不能编辑，也不显示画布**（只有闸门）。要「一边看一边改」需要另做只读渲染。
- 引入一个跨标签协议与其生命周期（心跳、租约、卸载让出），是本模块的新复杂度来源。
- 依赖 `BroadcastChannel`；不支持时退化为无锁（回到原风险），这一点是明确的降级而非静默失败
  （代码注释已写明）。

### Follow-up / Mitigation

- 若日后需要「多标签只读查看」：复用既有只读机制（节点 `data.readOnly` + `readOnlyNodeActions`
  + React Flow 关掉拖拽/连线），把闸门换成只读画布；**不要**为此放宽写权限。
- 同一浏览器不同 profile、隐身窗口与普通窗口之间不共享 localStorage，因此本锁无需覆盖它们
  （它们等价于不同设备，走节点级合并）。

## Pros and Cons of the Options

### Option A: 单写者编辑锁（已选）

- **Good**：正确性最强；实现与测试边界清晰；与既有「不可编辑 > 静默覆盖」口径一致。
- **Bad**：第二个标签不可编辑（连查看也不行）；需要跨标签协议。

### Option B: 跨标签协调

- **Good**：两个标签都能编辑，体验最好。
- **Bad**：需要把「丢弃本机未上传」与「保留本机未上传」拼接，边界多；出错时仍是静默丢数据。

### Option C: 按标签隔离存储

- **Good**：无需协议，两个标签自动等价于两台设备。
- **Bad**：关标签丢本地绘制缓存与未提交草稿；队列/配额等也得分标签，牵动面比看起来大。

### Option D: 只提示不改行为

- **Good**：改动最小。
- **Bad**：误删照旧发生，只是用户「被提前告知过」。
