### #0003 JSONB 缺 GIN 索引（**低**）

- **状态**: Won't Fix（2026-09-09 量化评估）
- **评估**: 全后端 SQL 扫描（`@>` / `<@` / `?` / `?|` / `?&` / `#>` / `#>>` / `->>` / jsonb_* 函数）**零命中**——`messages` / `grounding` / `custom_data` 及其他 JSONB 列（`details` / `snapshot_data` / `value`）均为整体写入（INSERT/UPDATE 原值）与整体读回（SELECT * 后应用层重建），无任何 JSON 操作符查询。GIN 索引在此模式下零读收益、纯写放大——且 `saveCanvas` 每次保存对 nodes 全删重插，写放大成本真实存在。
- **复开条件**：后续出现 JSON 操作符查询需求（如按 grounding 来源检索节点）时，先 `EXPLAIN` 实测再对命中列加 `jsonb_path_ops` GIN。

### #0083 管理端「画板总数」与用户列表口径不一致（**中**）

### #0092 内存模式的 `restoreAccount` 没有 partial unique index 的等价物（**低**）

- **状态**: Open（2026-09-16 登记）
- **背景**: `users.email` 的唯一性是**部分**唯一索引 `WHERE deleted_at IS NULL`（Spec F4），
  PG 侧因此允许「已注销账号与活跃账号同邮箱」。内存模式没有索引，`restoreAccount` 的内存分支
  也不做任何重复检查。
- **影响**: 仅在**内存/测试模式**下可能出现两个活跃用户持有同一邮箱；PG 侧由索引兜住并 409。
  ADR-0023 的「补绑邮箱」让这条路径变得更容易达到（给某个已注销账号占用的邮箱绑定成功后，
  再 restore 那个账号）。生产不受影响，故定为低。
- **修复**: 在 `restoreAccount` 的内存分支里跨用户查一次活跃重复，命中即抛 `code='23505'`
  的形状（与 `bindVerifiedEmail` 内存分支同款写法），使两模行为一致。
- **关联**: ADR-0005 / Spec F4、ADR-0023、`server/repositories/user.repository.ts`

### #0013 CSRF 防护不完整（**中**）

- **状态**: Done（2026-09-12，ADR-0020；做法与清单原处方不同，见下）
  - ✅ 变更方法同源守卫（`server/middleware/same-origin.ts`）：只作用于 `POST/PUT/PATCH/DELETE`；`Sec-Fetch-Site: cross-site` → 403；带 `Origin`（或可从 `Referer` 推导）且非同源 → 403；**不带 `Origin` 一律放行**——浏览器对跨站变更请求必带 `Origin`，故放行它不放松浏览器侧防线，而 curl / 服务端调用 / 支付宝回调 / 全部既有测试都不带
  - ✅ 会话 cookie 属性收口为单一事实源（`server/lib/session-cookie.ts`）；`tests/cookie-attributes.test.ts` 把 `HttpOnly` + `SameSite=Lax` + 无 `Domain` 从隐式防线变成会变红的显式契约
  - ✅ 全局 `express.urlencoded()` 收窄到支付宝通知单端点，去掉全局表单编码面
  - ✅ `arch-tests/csrf-guard.test.mjs` 补**接线**守护：`tests/csrf-same-origin.test.ts` 等行为测试都显式构造请求去打 `createApp()`，守卫挂错位置（挂在路由之后、或新路由挂在守卫之上）它们照样全绿
- **原处方为何被替换**（2026-09-12 复核）：清单写的是「给 SSE 端点加 `X-Requested-With` 校验」，核对后实际暴露面更小——cookie 已是 `httpOnly + sameSite:'lax'` 且无 `domain`，全仓无 CORS 中间件。真正的问题不是缺一道校验，而是整条防线**隐式**：谁把 cookie 属性改成 `sameSite:'none'` 不会有任何东西变红。故改为「显式同源守卫 + 属性契约测试」，比逐端点加 header 覆盖面更全且不会遗漏新增端点。
- **已知边界（已接受，记入 ADR-0020）**：`Origin` 与 `Sec-Fetch-*` 都是浏览器自愿提供的请求头，非浏览器客户端可任意伪造——本守卫防的是**用户浏览器被第三方页面驱动**（CSRF），不防伪造客户端（后者的边界仍是鉴权）。两个改状态的 GET（`verify-email`、`shares/:shareCode`）靠不可猜 token/code 自保，不改。
- **关联**: 报告 §8.3、ADR-0020、`tests/csrf-same-origin.test.ts`、`tests/cookie-attributes.test.ts`

- **收口路径（若决定做）**: 改由服务端权威记录「该节点已推理过」——在 chat 路由按 `(canvas_id, node_id)` 落一条持久记录（新表或 `nodes` 新列），计数改以它为准；服务端写入故不受客户端左右。代价：新表/列 + 迁移 + **该表必须按 ADR-0019 归类进 RLS 覆盖面**（`arch-tests/rls-coverage.test.mjs` 强制：未归类即红）+ chat 写入点 + 用例回归。

- **关联**: `server/repositories/canvas.repository.ts`（`countCanvasNodes`）、`src/components/canvas/DeepDiveCanvas.tsx`（`localUsed` 镜像口径）、`docs/产品问题跟踪清单.md` D2、#0021、安全发布 checklist §1/§4

### #0091 绑定第三方登录只凭「有有效会话」，不再验证密码（**中**）

- **状态**: Open（2026-09-16 登记）——当前是**已明确接受的边界**，登记是为了让「将来决定收口」时有现成路径
  - 补充（2026-09-16 同日）：微信登录的前端入口与绑定 UI 已随「只支持邮箱注册登录」一并移除
    （用户侧确认开放平台凭据不具备网站应用登录能力），故本条目前**处于休眠**——后端绑定接口
    仍在但前端不再有可达入口。将来恢复绑定能力时本条即刻生效，收口路径不变。
- **背景**: ADR-0023 把「有效会话」定为绑定的授权依据（登录弹窗只在未登录时可达、绑定按钮只在已登录时可见，
  「有没有会话」正好等价于用户心智；也让回调顺手堵掉「已登录浏览器经书签触发静默换账号」）。
- **影响**: 在解锁的共享/二手设备上，短暂接触设备的人扫**自己的**微信即可在受害者账号上留下一个
  **持久登录凭据**。叠加两点会放大：① ADR-0023 刻意不提供用户自助解绑；② 手机号被回收后微信号可能易主。
- **缓解（已在位）**: 运营台 `DELETE /api/admin/users/:id/oauth/:provider` 可解除绑定（审计 `admin_oauth_unbind`）；
  前端在绑定入口明示「绑定为一次性操作，如需解除请联系客服」；一账号只允许一个微信身份（不会累积多个凭据）。
- **收口路径（若决定做）**: ① 绑定前要求重新输入密码（仅对 `has_password === true` 的账号可行，
  纯微信账号没有更强的凭据可验）；② 或引入**绑定意图 cookie**：个人中心的「绑定微信」先打一个
  短时效 httpOnly 标记（写入点仍只能是 `server/lib/session-cookie.ts`），回调必须带它才按绑定处理，
  否则一律按登录——这样「临时会话 + 手工访问 /authorize」就不再具备绑定效力。
- **关联**: ADR-0023、ADR-0022、`server/routes/wechat.ts`（`resolveSessionUser` / `handleBind`）、
  `server/services/admin.service.ts`（`unbindOAuthIdentity`）

### #0093 出站守卫只看字面主机名，DNS rebinding 仍可绕过（**中**）

- **状态**: Open（2026-09-16 登记，与 ADR-0024 同批；ADR 已就此**明说残留**而非假装覆盖）
- **背景**: ADR-0024 的出站守则是「解析 URL → 校验字面主机名/协议/内网段」，**不做 DNS 解析后再按 IP 复核**。
- **影响**: `ai_model_config.openai_base_url` 填一个**公网域名**、其 A 记录指向 `127.0.0.1` 或内网地址时，
  守卫看到的是合法公网主机名 → 放行 → 服务端实际连到内网/本机服务（含云元数据若其 IP 被判为公网域名指向）。
  前提：攻击者需能控制一个域名 + 管理员会把它填进模型配置（或通过其它未来新增的「用户可影响出站目标」的入口）。
- **缓解（已在位）**: 该地址只能由**管理员**在运营台填写（非用户可达）；掩码密钥回落已绑定主机（H2 修复，
  密钥不会被送到「请求里临时指定的新地址」）；元数据 IP 字面量与 `metadata.*` 主机名恒定拒绝。
- **收口路径（若决定做）**: ① 出站前 `dns.lookup` 拿到 IP 再跑一次内网段判定（注意 TOCTOU：解析与连接之间
  DNS 仍可变）；② 真正稳的做法是**固定连接目标**——自建出网代理 / 用 `undici` 的 `connect` 自定义 lookup，
  把「解析 → 校验 → 连接」落到同一个 IP 上。
- **关联**: ADR-0024、`server/lib/outbound-url.ts`、`server/services/ai.service.ts`（`resolveOpenAiEndpoint`）

### #0096 载入以服务端为准：本机未上行内容被静默丢弃，UI 缺离线/未保存口径（**中**）

- **状态**: Done（2026-09-18）
- **背景**: ADR-0025 把载入路径收口为「取到服务端内容即采用」，这是 ADR-0021「无网不可编辑」
  的彻底化——离线编辑、弱网/刷新前没传完的编辑，在下次载入时会被**静默丢弃**，且没有任何提示。
  当前顶栏只有泛化的「同步失败，已停止自动重试」，用户无法判断「我现在的编辑会不会被丢」。
- **影响**: 用户在断网/弱网下继续编辑会白做；极端情况下（页面被系统杀掉、企业网络拦断上传）
  用户直到重新载入才发现内容没了，且无从追溯。
- **收口（2026-09-18，三件事全部落地）**:
  1. **保存调度兜底**：内容类变更仍走 600ms 防抖，结构操作（新增/删除节点或边、连边）与提交点
     （拖拽结束、便签/标题失焦、折叠）改为**立即落库**，判据在 `src/lib/canvas-change.ts`
     （纯函数 + `tests/canvas-change.test.ts`）；切换画板/新建画板/导入前先
     `flushPendingCanvasSave()`，页面隐藏前**先 flush 再 keepalive 补传**（顺序不可反）；
     AI 流式回答按 2s 强制落盘并在卸载时 abort。窗口从「秒级」压到 RTT 级。
  2. **离线/未保存态口径**：新增 `online` 状态（`online/offline` 事件 + 断网 toast）；顶栏同步图标
     拆出 `offline` 维度，文案改为「当前无网络，改动暂时无法保存到云端 / 有改动尚未保存到云端
     （已停止自动重试）/ 正在保存到云端…」；进入慢速自愈（`syncState === 'error'`）时补一次 toast
     ——此前只有红云图标，没有文字告知。
  3. **丢弃前的可感知提示**：`unsavedDiscardRisk = 有未确认内容 && (离线 || error || conflict)`，
     命中时切换画板/新建画板/导入备份前 `window.confirm` 拦住并说明原因；风险态下注册
     `beforeunload` 拦住刷新/关闭。**无风险时不弹**，不打扰正常使用。
- **关联**: ADR-0025（Negative Consequences 与 Follow-up）、ADR-0021 残留风险 1、`src/lib/storage.ts`
  （`fetchBoardFromServer` 三分支）、`src/lib/canvas-change.ts`、`src/App.tsx`（同步状态/toast/
  离开前确认）、`src/components/ui/Topbar.tsx`（同步指示）

### #0097 同一浏览器多标签页共享 blob/基线，同时编辑同一块画板会互相覆盖（**中**）

- **状态**: Done（2026-09-18）
- **背景**: 画板 blob（`deepdive_board_*`）、服务端版本小键（`deepdive_board_server_ts_*`）、
  节点级差分基线（`deepdive_board_base_*`）与同步队列都是 **localStorage 共享、不按标签页隔离**，
  而两个标签各自的 React 状态与内存里的画布是独立的。两个标签同时打开同一块画板时：
  - 后写的标签会用自己内存里的整块板覆盖共享 blob（可能抹掉另一标签刚保存的节点）；
  - 基线被任一标签推进后，另一标签按新基线做差分，会把自己「没见过」的节点判成本地删除 →
    冒墓碑删掉对方刚保存的内容。
  ADR-0025 只保证「载入以服务端为准」，不解决标签页之间的一致性。
- **影响**: 同浏览器多标签同时编辑同一画板时可能互相覆盖或误删（数据在服务端被删，非仅本地）。
- **收口（2026-09-18，ADR-0026）**: 采用 **单写者编辑锁**（`src/lib/board-edit-lock.ts`，
  BroadcastChannel + 心跳/租约 + tabId 字典序决胜 + force 接管）。非持有标签不渲染编辑画布，
  改为 `BoardLockedNotice`（说明 +「在此标签页继续编辑」+「打开画板库」）；破坏性操作在非持有者上
  一律拒绝并提示。两个候选被否：跨标签合并（要把「丢弃本机未上传」与「保留本机未上传」拼接，
  边界多）与按标签隔离存储（关标签丢绘制缓存/草稿）。
  - ⚠️ 接管必须**先按服务端对齐再拿锁**，否则中间那次防抖保存会拿旧画面做差分，把对方的节点
    当成本地删除（见 `handleTakeOverEdit` 注释）。
  - 单测逼出一个真 bug：`release()` 若先广播再清本地状态，对方收到 release 后立刻 claim 并
    **同步回投**给我，我会重申 claim 把对方刚拿到的锁打掉 → 两个标签都只读。已改为先清状态再广播。
- **残留**: 第二个标签不能编辑也不能查看（要「一边看一边改」需另做只读渲染，见 ADR-0026 Follow-up）；
  环境无 `BroadcastChannel` 时退化为无锁（代码注释已写明是降级）。
- **关联**: ADR-0026（本条收口决策）、ADR-0025、`src/lib/board-edit-lock.ts`、
  `src/components/ui/BoardLockedNotice.tsx`、`tests/board-edit-lock.test.ts`
