### #0003 JSONB 缺 GIN 索引（**低**）

- **状态**: Won't Fix（2026-09-09 量化评估）
- **评估**: 全后端 SQL 扫描（`@>` / `<@` / `?` / `?|` / `?&` / `#>` / `#>>` / `->>` / jsonb_* 函数）**零命中**——`messages` / `grounding` / `custom_data` 及其他 JSONB 列（`details` / `snapshot_data` / `value`）均为整体写入（INSERT/UPDATE 原值）与整体读回（SELECT * 后应用层重建），无任何 JSON 操作符查询。GIN 索引在此模式下零读收益、纯写放大——且 `saveCanvas` 每次保存对 nodes 全删重插，写放大成本真实存在。
- **复开条件**：后续出现 JSON 操作符查询需求（如按 grounding 来源检索节点）时，先 `EXPLAIN` 实测再对命中列加 `jsonb_path_ops` GIN。

### #0005 ID 风格不统一（~~高~~ → **低**，P0 已解除）

- **状态**: Won't Fix（2026-09-12 复核改判；生成侧已收口 2026-09-10）
  - ✅ 生成侧统一 UUIDv7（`src/lib/uuid.ts`，路线 A 渐进式）：画板/节点/边/分支导出板等全部新实体恒 36 字符、不可枚举、时间前缀 B-tree 友好；ADR-0013 前缀截断防御随之移除并 Deprecated
  - ⬜ 剩余：存量行仍为旧格式 VARCHAR（混存兼容，无功能影响）
- **改判理由**（2026-09-12）：原条目按 P0 登记，风险是「id 可枚举 → 可遍历他人资源」。生成侧全部改用 UUIDv7 后该风险已消除（属主制仍是安全边界，见 ADR-0004/0016/0018），剩下的只是**存量行的列类型不一致**——无查询正确性问题、无越权面，代价却是「改 uuid 列 + 重写全部 FK 与 JSONB 内嵌 parentId」，收益与风险倒挂。
- **复开条件**：下次做「列类型/结构大版本迁移」时一并处理（顺带清 `varchar(64)→255` 的历史人工变更）；或出现依赖 id 类型的实际故障。
- **关联**: 报告 §13.1、ADR-0013（已 Deprecated）

### #0083 管理端「画板总数」与用户列表口径不一致（**中**）

- **状态**: Done（2026-09-10）
  - 根因：`getAdminOverview.totalCanvases` / `/api/db/status.canvasCount` 原为全局 `COUNT(*) FROM canvases WHERE deleted_at IS NULL`，**不排除已注销用户（F4 软删）的画板**；而 `listAdminUsers` 只列 `users.deleted_at IS NULL` → `sum(列表 canvas_count) ≠ 画板总数`（另叠加列表分页）
  - 统一口径：overview 与 db-status 的画板/节点/用户计数均 `JOIN users ... WHERE u.deleted_at IS NULL`（内存分支同款过滤），与用户列表一致
  - 内存 `cleanupDeletedUsers` 原只删 sessions、不级联删画板（PG 靠 FK `ON DELETE CASCADE`）→ 硬清理后残留孤儿画板仍被统计；补 `purgeUserDataMemory`：级联删画板与相关分享、AI 日志 `canvas_id` 置空
- **影响**: 有注销用户时两处数字必然对不上，管理员无法对账；内存/ PG 双模行为漂移
- **关联**: #0082、#0001、F4 注销语义

### #0084 画布旧写路径与 legacy 默认板模式待下线（**低**，有明确触发条件）

- **状态**: Open（2026-09-12 登记，画布同步重构阶段 6）
- **影响**: 为灰度共存保留的两套代码还在，属于**有到期日的临时复杂度**，不是缺陷：
  - 服务端 `saveCanvas` 的整板替换分支（`protocolVersion` 缺失 / `1`）+ `SAVE_LEGACY_REPLACE_ENABLED` 开关；
  - `SAVE_DEFAULT_BOARD_MODE=legacy` 的共享放行分支（`isSharedDefaultCanvas`）；
  - 客户端 `storage.ts` 里 409 的旧处理与 legacy 相关注释。
- **修复（顺序不可交换，见 `docs/部署与回退手册.md` §5.1）**:
  1. 客户端全面发 `protocolVersion: 2` 并 soak ≥7 天，确认 `[canvas-save]` 日志 `mode=replace` 归零（翻之前当日 `pg_dump`）
  2. `SAVE_LEGACY_REPLACE_ENABLED=false` → 观察一周无 `CLIENT_OUTDATED` 异常
  3. 删除服务端整板替换分支与其单测；再评估删除 `SAVE_DEFAULT_BOARD_MODE` 开关、把 `isSharedDefaultCanvas` 的放行分支一并移除
- **不做会怎样**: 两套写入语义长期并存，任何人改 `saveCanvas` 都要同时维护两条路径——这正是本项目最贵的一类复杂度
- **关联**: ADR-0017、ADR-0018、`docs/部署与回退手册.md` §5.1

### #0016 密码校验阻塞事件循环（**中**）

- **状态**: Won't Fix（2026-09-09 评估）
- **评估**: 前提不成立。`server/lib/crypto.ts:22` 用的已是 `crypto.scrypt` **异步回调形态**——该 API 将 KDF 卸载到 libuv 线程池执行，**不阻塞事件循环**；阻塞事件循环的只有 `scryptSync`（项目未使用）。
- **"登录风暴延迟累加"的真实机理**：线程池排队（默认 4 线程被 200ms KDF 占满，后续请求等待空位）。缓解手段是部署层调大 `UV_THREADPOOL_SIZE`（如 8-16），属部署调优参数而非代码缺陷。
- **拒绝 worker_threads 处方的理由**：Node 自身线程池就是官方推荐的异步 scrypt 用法，再包一层 worker_threads 只增加进程/线程管理与复杂度，无任何收益。

### #0018 审计日志查询性能待优化（**低**）

### #0044 数据库备份策略不完整（**中**）

- **状态**: Open（复核 2026-09-12：已有「发布时备份」，缺「定期备份与演练」）
  - ✅ CD deploy 每次发布自动 `pg_dump` 到快照 `db/arborize_<TS>.sql.gz`（失败即中止发布），服务端快照保留最近 5 份；恢复命令写在快照 `RELEASE_INFO.txt` 与手册 §5（见 `docs/部署与回退手册.md`）
  - ⬜ 剩余：备份**只随发布产生**——长期不发版就没有新备份；无异地对象存储副本（构建机 `backups/` 是手工维护）；无 RPO/RTO 目标；**从未做过恢复演练**
- **影响**: 已能覆盖「发布搞坏了」这一最常见场景；覆盖不了「不发版期间数据被误删/损坏」与「备份本身不可用」
- **修复**:
  1. 独立于发布的定时 `pg_dump`（cron + 对象存储），保留策略明确
  2. 写清 RPO/RTO 目标（与本项目实际：单机 PG，RPO 现实值 = 备份间隔）
  3. 做一次实际恢复演练并记录耗时（当前 `arborize` 库体量小，成本很低）
- **关联**: 报告 §10.5、ADR-0017（墓碑 GC 与旧写语义停止后**只能**靠备份回滚）
