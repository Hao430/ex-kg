# Spec P1 — 反馈工单处理通道

> 来源：产品问题跟踪清单——「反馈只进库，处理通道还没建」：`POST /api/feedback` 双模入库后，运营台无列表、无回复/状态流转 API、用户无查看入口，管理员只能登服务器直查库。
> 状态：已实施（2026-09-17）
> 关联：H1 显式列投影纪律（`ADMIN_USER_COLUMNS` 先例）、F2 审计日志（`recordAuditLog`）、ADR-0019 作用域纪律、ADR-0016 运营台聚合是 admin 保留的跨租户能力

## 1. 问题与现状

- 提交链路已就绪：`FeedbackModal`（可匿名）→ `POST /api/auth/feedback`（`auth.ts`，`/api/feedback` 是同一 handler 的别名挂载，`app.ts:121`）→ `feedback.repository.ts` 双模入库。响应 201 + `feedbackId`。
- 表结构早预留了工单处理全部字段——`status`（默认 `pending`）、`admin_reply`、`resolved_by`、`resolved_at`、`updated_at`，并建了 `idx_feedbacks_status(status, created_at DESC)`（schema.ts:374-393、562）——但全仓没有任何代码读写它们。「建了地基没盖房」。
- `feedbacks` 已归 `RLS_DIRECT_USER_TABLES`（schema.ts:21，谓词 `user_id = app.user_id`）；`admin.ts` 路由级已挂 `authMiddleware + requireAdmin + runWithSystem`（admin.ts:36-40）——新增 admin 端点**零作用域接线**即跨租户可用。
- **现状缺陷 A（既有 bug，本 Spec 一并修）**：前端 `FeedbackType = 'suggestion' | 'bug' | 'ux' | 'other'`（`src/types.ts:120`，FeedbackModal 含「体验优化」选项），但后端 `FeedbackSchema` zod enum 只有 `['suggestion','bug','other']`——选「体验优化」提交**必然 400**，用户看到的是笼统的提交失败。
- **现状缺陷 B**：`POST /feedback` 无任何限流。匿名可写端点 + 无 limiter = 入库垃圾数据敞口（同文件其他端点均有独立 limiter，唯此端点漏配）。
- `notifications` 表已在 schema 建好但全仓零引用（与 #0004 空壳表同类），本次不搭车。

## 2. 目标与非目标

**目标**

1. 运营台新增「反馈工单」页签：列表（状态/类型过滤 + 分页）+ 状态流转 + 回复，`resolved_by`/`resolved_at` 首次进入终态时落值。
2. 用户侧新增「我的反馈」查看入口：登录用户可看自己提交的工单的状态与回复（读路径走 RLS 天然隔离）。
3. 修复 `'ux'` 枚举分叉（后端补齐）；给 `POST /feedback` 补独立限流器。
4. admin 变更写审计日志（`recordAuditLog`，action `admin_feedback_update`）。

**非目标**

- 不做回复的邮件/站内通知：匿名或仅留微信号 `contact_info` 的工单本就不可达邮件，站内「我的反馈」是主通道；邮件通知留待后续单独评估。
- 不做工单删除/垃圾清理接口（`DELETE`）——首版以状态流转消化垃圾数据（`rejected`）。
- 不搭车启用 `notifications` 表（#0004 评估范围）。
- 不给 FeedbackModal 提交表单改版（提交链路行为逐字不变）。

## 3. 设计

### 3.1 数据层（零 schema 变更）

- `status` 状态机四态：`pending → processing → resolved | rejected`，且 `pending` 可直达 `resolved | rejected`；终态（`resolved`/`rejected`）**不可再流转**。流转合法性在 service 层用显式 map 校验（非法流转 400 `FEEDBACK_INVALID_TRANSITION`），zod 只校验形状。
- 进入 `resolved` **必须**带非空 `admin_reply`（回复是「已处理」的载体）；`rejected` 回复选填。
- 首次进入终态：`resolved_by = req.user.id`、`resolved_at = NOW()`；此后修订 `admin_reply` 不改这两个字段（谁定的案保持谁）。`updated_at = NOW()` 由 UPDATE 语句显式推进（PG 无触发器，内存分支手动赋值）。
- `records.ts` 的 `FeedbackRecord` 扩展五字段：`status` / `admin_reply` / `resolved_by` / `resolved_at` / `updated_at`。`createFeedback` 内存分支**显式**写默认值（`status:'pending'`、`admin_reply:''`、`resolved_by:undefined`、`resolved_at:undefined`、`updated_at:now`）——PG 有列默认值、内存没有，这是双模分叉点；PG 分支 `RETURNING *` 的映射同步补五键。
- **不新增迁移**：五列与索引已在 schema.ts 中，`docs/数据库建表脚本.sql` 无需改动。

### 3.2 后端 API

**`GET /api/admin/feedbacks`**（挂在既有 admin 路由，自动继承 requireAdmin + system 作用域）

- Query：`status?`（枚举）、`type?`（枚举）、`page?`、`limit?`（≤100，默认 20），`ORDER BY created_at DESC`。
- 响应 `{ feedbacks, total, statusCounts }`；`statusCounts` 是一条 `GROUP BY status`（内存分支 reduce），供页签角标。
- **显式列投影**（H1 纪律，`ADMIN_USER_COLUMNS` 先例）：`id, user_id, user_email, type, rating, content, contact_info, status, admin_reply, resolved_by, resolved_at, created_at, updated_at`——feedbacks 无敏感凭据列，但禁止 `SELECT *`（列演进时会静默外泄）。两个分支**共用同一个视图函数**（先例 `toAdminUserView`：PG 返回 Date、内存是 ISO 串，时间戳归一 `toIsoOrNull`）。
- 读限流：独立实例 `adminFeedbackReadRateLimiter`（60/min per user）——不与 `adminLogReadRateLimiter` 共桶（#0089 教训：不同流量不共额度）。

**`PUT /api/admin/feedbacks/:id`**

- Body：`{ status, admin_reply? }`（zod：`status` 四态枚举、`admin_reply` ≤2000 可选）。
- 校验链：工单不存在 404 → 流转非法 400 → `resolved` 缺非空回复 400 → 通过则条件更新并落 `resolved_by/resolved_at/updated_at`。
- 复用 `adminUserWriteRateLimiter`（admin 写端点共用一桶的既有惯例，流量极低）。
- 审计：`recordAuditLog({ userId: req.user.id, action: 'admin_feedback_update', targetType: 'feedback', targetId: id, details: { from, to } })`——不落工单正文与联系方式（审计/运营日志详情不得落分享码等只读凭据的同类纪律）。

**`GET /api/feedback`**（GET 挂在既有 `authRouter` 的 `/feedback` 路径上，别名挂载使 `/api/auth/feedback` 同样可达）

- `authMiddleware` 路由级中间件（POST 是可选认证故未挂；GET 必须登录，未登录 401）。
- 走 `authMiddleware` 建立的 `runWithUser` 作用域：PG 下 RLS 谓词 `user_id = app.user_id` 天然只回本人行，**仓储不得自行加作用域**（tenant-filter 纪律）；内存分支显式 `user_id === req.user.id` 过滤。
- 匿名提交的工单 `user_id` 为 NULL，任何人都看不到——匿名反馈的回执通道只有提交时自填的 `contact_info`，这是产品语义不是缺陷。
- **用户视图列白名单**：`id, type, rating, content, status, admin_reply, resolved_at, created_at, updated_at`——不含 `resolved_by`（内部 admin uuid）、`contact_info`/`user_email`（无必要回吐）、`user_id`。
- 独立限流 `feedbackMineReadRateLimiter`（30/min per user，user 回落 IP）。

**`POST /feedback` 补限流**：独立实例 `feedbackSubmitRateLimiter`（5/h per IP，对齐 signup/forgot 档位；既有测试 a1 仅单次提交，不受影响）。enum 同步补 `'ux'`。

### 3.3 前端运营台（AdminDashboardModal）

- `activeTab` 联合类型扩 `'feedback'`，导航排 `orders` 之后；进入页签才拉取（对齐 orders 的 useEffect 门控先例，admin.ts:185 模式）。
- 列表卡片：类型徽章 + 评分星 + 状态徽章（pending 灰 / processing 蓝 / resolved 绿 / rejected 深灰）+ 正文 + 提交者（`user_email` 或 `contact_info`，匿名标「匿名」）+ 相对时间。
- 操作区：状态下拉（仅展示合法流转项）+ 回复 textarea + 保存；终态工单回复仍可修订（不改 resolved_by/resolved_at 的语义对用户透明）。
- 过滤 chips：全部 / 待处理（角标 = statusCounts.pending）/ 处理中 / 已解决 / 已驳回；类型下拉。

### 3.4 前端用户侧（FeedbackModal）

- 顶部加二段切换：「提交反馈」（现有表单，逐字不动）/「我的反馈」（仅登录态显示；游客只有提交页）。
- 「我的反馈」为列表：状态徽章 + admin_reply（空则「暂无回复」）+ 时间；不提供匿名工单查询。
- 提交成功的 2s 停留页文案不变。

**实施边界决策**（与提案的差异）

- 同状态提交视为**幂等修订**（允许 `resolved → resolved` 改回复），不算「流转」；只有换状态才查转移表——否则「终态后修订回复」这条需求无法实现。
- 工单 id 先经 zod `uuid()` 校验（畸形 id 返回 400，而不是让 PG `22P02` 冒成 500/误落内存）。
- 运营台工单列表在**弹窗打开时即拉取**（而非进入页签才拉），以便页签角标在其它页签也可见；`statusCounts` 不受状态过滤影响、受类型过滤影响。

## 6. 风险

- **双模语义漂移**（中）：五字段的默认值与归一化靠「#1 默认值 + #6 键集合」两组用例钉死；改任一分支漏改另一边会红。
- **匿名工单不可达**（中，产品语义）：匿名提交者在站内永远看不到回复，只能靠 `contact_info` 人工触达——运营台卡片把 `contact_info` 放显著位置缓解。
- **AdminDashboardModal 体量**（低）：文件已达 1524 行，本 Spec 只做页签级增量，不搭车拆分（组件拆分是独立技术债议题）。
- **限流档位**（低）：5/h per IP 对正常用户足够（一次会话至多一两条），被恶意刷时 429 文案引导走客服渠道。
