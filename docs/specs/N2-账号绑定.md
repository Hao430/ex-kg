# Spec N2 — 账号绑定（微信 ↔ 邮箱，单向）

> 来源：N1（微信扫码登录）上线后发现的缺口工单——「既有邮箱账号的用户点了微信登录会静默建出第二个账号」（2026-09-16）
> 状态：已实施（2026-09-16）
> 关联：ADR-0023（本 Spec 的架构决策）、ADR-0022（微信登录）、ADR-0019（RLS/作用域）、ADR-0007（独立限流器）、Spec D3（邮箱验证码基建）、Spec F4（注销软删）
> 已确认的产品口径：① 个人中心双向绑定入口；② **补绑邮箱不设密码**；③ 所有账号都显示「绑定微信」；④ 有有效会话时回调**一律按绑定**处理；⑤ 不做用户自助解绑，但加**运营台解绑逃生舱**

## 1. 问题

微信 `snsapi_login` 不返回邮箱、也不返回手机号，服务端**没有任何办法**自动认出
「这个微信号就是 alice@example.com」。于是 N1 的行为是：邮箱账号的用户点了微信登录 →
按 openid 查无身份 → **建一个全新的空账号** → 用户的画板/VIP 全在原账号，且不会被告知发生了什么。

同一批遗留问题：

1. 纯微信账号的邮箱是占位地址、口令是不可满足的哨兵 → **无法邮箱登录、无法自助找回**；
2. 已登录的浏览器经书签/旧标签页直接访问 `/api/auth/wechat/authorize`，原实现会
   **建出第二个账号并覆盖会话 cookie**（用户在自己没察觉的情况下换了账号）。

## 2. 目标与非目标

**目标**

1. 打通唯一可行的「既有账号 + 微信」路径：**先登录 → 在个人中心绑定微信**；
2. 让绑定成为回调的默认语义（有会话即绑定），顺带堵掉上面第 3 条隐患；
3. 解掉纯微信账号的账号生命周期缺口：补绑邮箱 → 忘记密码 → 邮箱+密码登录 → 可自助找回；
4. 误绑有退路；提醒用户去绑定。

**非目标**

- 不做用户自助解绑（单向绑定）；不实现自动合并（技术上做不到）；
- 不做换绑邮箱（只有占位邮箱的账号能补绑，天然规避）；
- 不落任何微信 token；不新增环境变量。

## 3. 设计

### 3.1 回调分流（`server/routes/wechat.ts`）

state 校验通过 → 读 `session_token` 判定：

| 情形 | 结果 |
| :--- | :--- |
| 有效会话 + 该微信未绑 | `linkOAuthIdentity`（`runWithUser`）→ 审计 `wechat_bind` → 302 `/?wechat=bound` |
| 有效会话 + 该微信已绑本账号 | 幂等 → `/?wechat=bound` |
| 有效会话 + 该微信已绑他人 / 本账号已有另一微信 | `/?wechat_bind_error=WECHAT_ALREADY_BOUND` |
| 无会话 / 会话失效 / 账号冻结 | 登录路径（N1 原逻辑），回跳**仍是** `/?wechat=ok` |

绑定分支：**不建账号、不改会话 cookie**。

### 3.2 补绑邮箱（`server/services/account-binding.service.ts` + `routes/auth.ts`）

| 端点 | 请求体 | 说明 |
| :--- | :--- | :--- |
| `POST /api/auth/bind-email/send-code` | `{email}` | 复用验证码基建；主题 `枝想 邮箱绑定验证码`；60s 冷却 |
| `POST /api/auth/bind-email` | `{email, code}` | **不含密码**；`email_verified` 保持 TRUE；不踢会话 |

守卫：仅占位邮箱账号可补绑（否则 400 `EMAIL_ALREADY_BOUND`）；目标不得是 `@wechat.invalid`
（400 `EMAIL_DOMAIN_RESERVED`）；全站唯一性预检（409 `EMAIL_EXISTS`，**跨租户**）；
`23505` 兜底同为 409。

`password_hash` 保持哨兵 → `has_password` 仍为 false、修改密码表单继续隐藏；
用户想邮箱登录走「忘记密码」自助设置（个人中心有文案指引）。

### 3.3 绑定状态与提醒

- `/me` 追加 `wechat_bound` / `wechat_nickname`（**只在 `/me` 查**，不进 `publicUser()`）；
- 个人中心「账号标识与绑定」卡片＝邮箱行 + 微信行（含就地展开的邮箱+验证码子表单）；
  顺带修掉 N1 遗留的徽章错误推断（原先仅凭「邮箱是不是占位」就断言「微信账号已绑定」）；
- 提醒由 `email_placeholder` 驱动（不用 URL 参数），去重标记按账号分键
  （`src/lib/bind-nudge.ts`）。

### 3.4 运营台解绑

`DELETE /api/admin/users/:id/oauth/:provider`（仅 `wechat`），审计 `admin_oauth_unbind`，
未绑定 → 404。

## 6. 实现中修掉的两个真问题

1. **审计里的 `oldEmail` 在内存模式下会等于新邮箱**：内存分支的 `findUserById` 返回的是
   Map 里的**活对象引用**，`bindVerifiedEmail` 直接改它 —— 事后再读 `user.email` 拿到的已是新值。
   PG 分支返回新行对象、没有这个现象，即一处**只在内存模式发生的双模分叉**。
   改法：UPDATE 之前把旧邮箱取成局部常量。（由 `email_bind` 审计用例抓出。）
2. **`EMAIL_ALREADY_BOUND` 与 `EMAIL_DOMAIN_RESERVED` 的判定顺序**：前者在
   `loadBindableUser` 里先执行，所以真实邮箱账号请求占位域时得到的是
   `EMAIL_ALREADY_BOUND`（账号根本不合格）。这是正确语义，测试按此断言。

## 7. 风险与已知边界

- 补绑邮箱不设密码 ⇒ 用户想邮箱登录须自己走一次「忘记密码」。
- 绑定只凭有效会话、不再验证密码：解锁的共享设备上，攻击者扫自己的微信可在受害者账号留下
  持久凭据；缓解＝运营台解绑 + 前端明示「绑定为一次性操作」；重验证记入技术债。
- 一账号一微信身份，用户不能自助解绑。
- 会话失效时回落为登录。
- 目标邮箱属于已注销账号时可绑成功，副作用是该账号此后无法被 restore（管理员需先改邮箱）。
- 内存模式 `restoreAccount` 无 partial unique index 等价物（仅测试环境），记入技术债。
