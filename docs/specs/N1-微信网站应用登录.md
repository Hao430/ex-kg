# Spec N1 — 微信开放平台「网站应用」扫码登录

> 来源：用户提出的「接入微信登录能力」（2026-09-16）
> 状态：已实施（2026-09-16）
> 关联：ADR-0022（本 Spec 的架构决策）、ADR-0019（RLS/作用域）、ADR-0020（同源守卫与 cookie 单一事实源）、ADR-0014（支付宝回调的对照）、Spec F4（注销软删）
> 已确认的产品口径：① 已有已审核的网站应用，走真实渠道；② 首次微信登录**自动建号并登录**；③ 身份落新表；④ 入口为**整页跳转扫码**

## 1. 问题

当前只有邮箱 + 口令一种登录方式。接入微信登录有三个绕不开的约束：

1. **微信不返回邮箱也不返回口令**（`sns/userinfo` 只有 `openid`/`unionid`/昵称/头像，
   自 2021-10-20 起性别与地区已不再返回），而 `users.email` 与 `users.password_hash`
   都是 `NOT NULL`（partial 唯一索引只在 `deleted_at IS NULL` 时约束 `email`）。
2. **回调必然是浏览器顶层 GET 导航**（微信只支持 302 回跳），而 `same-origin.ts` 的
   `MUTATING_METHODS` 刻意只含 `POST/PUT/PATCH/DELETE`，即回调端点不受同源守卫保护，
   但它偏偏要建账号、下发会话。
3. **回调的 `code` 只能用一次、10 分钟过期**，所以不能像 `/verify-email` 那样
   「先给前端一个 token、由前端再调后端」——必须由服务端在回调里一次做完。

## 2. 目标与非目标

**目标**

1. 新增微信扫码登录，与邮箱登录**共用同一套会话、用户、配额、VIP 与 F4 注销语义**。
2. 首次微信授权即建号并登录；不强制先绑邮箱。
3. 一个微信用户不因重复授权/并发授权被建出第二个账号。
4. 不破坏既有防线：RLS 分类、作用域纪律、同源守卫、限流器独立性、双模持久化。
5. 零新增 runtime 依赖。

**非目标**

- 不做弹窗内嵌二维码（不引入 `res.wx.qq.com` 的 `wxLogin.js`）；
- 不做公众号网页授权（那是 `mp.weixin.qq.com` 的另一套接口与 scope）；
- 不做解绑 / 绑定邮箱流程，不保存 `access_token`/`refresh_token`；
- 不改 `users` 表结构（不加列、不放宽 NOT NULL）。

## 3. 设计

### 3.1 数据模型

新表 `oauth_identities`（`server/core/schema.ts`，归入 `RLS_DIRECT_USER_TABLES`）：

| 列 | 说明 |
| :--- | :--- |
| `user_id` | FK → `users(id)` `ON DELETE CASCADE` |
| `provider` | `'wechat'` |
| `openid` | 应用维度唯一标识 = **身份键**（`UNIQUE(provider, openid)`） |
| `unionid` | 开放平台主体维度标识；**普通索引，非唯一**（同一个人在不同应用下各占一行，unionid 相同） |
| `nickname` / `avatar_url` | 首次授权时的快照 |

无 `deleted_at`（身份是凭据映射而非用户数据）：软删用户时**不动**本表，F4 语义由
「JOIN 出的 `user.deleted_at`」判定；30 天硬删由 FK CASCADE / 内存分支
`purgeUserDataMemory` 清理。

### 3.2 占位账号

微信账号在 `users` 里表现为：`email = wx_<sha256(openid)[0:32]>@wechat.invalid`（确定性）、
`password_hash = OAUTH_UNSET_PASSWORD_HASH`（不含冒号 → `parseAndVerify` 立即返回 false）、
`email_verified = true`（否则 chat 被 `EMAIL_NOT_VERIFIED` 拦死）、
`name =` 昵称清洗后按码点截断到 50（`VARCHAR(100)`，与 zod `max(50)` 口径一致）。

服务端派生两个标记供 UI 使用（**不加数据库列**）：
`email_placeholder`（是否占位邮箱）、`has_password`（口令是否可用）。

注册口（`signUp` / `sendRegisterCode`）拒绝 `@wechat.invalid`，否则可被抢注造成
受害者微信首登的定向 DoS。

### 3.3 端点（`server/routes/wechat.ts`，挂 `/api/auth/wechat`）

| 端点 | 限流 | 行为 |
| :--- | :--- | :--- |
| `GET /authorize` | 20/min per IP | 未配置 → 302 `/?wechat_error=NOT_CONFIGURED`；否则种 state cookie 并 302 到 `open.weixin.qq.com/connect/qrconnect` |
| `GET /callback` | 30/min per IP（超限 302 回 `RATE_LIMITED`） | state 校验 → 换 code → 取资料 → find-or-create → 下发会话 → 302 `/?wechat=ok` |
| `GET /status` | 60/min per IP | `{enabled}`，供前端决定是否渲染入口（兼运维探针） |

`redirect_uri` 由 `resolveOrigin(req)`（优先 `APP_URL`）推导，**不单设环境变量**。
回跳目标硬编码，不接受任何用户提供的 returnUrl。

### 3.4 登录编排（`server/services/wechat.service.ts`）

1. 身份命中且账号未注销 → 直接登录（`resetFailedLogin` 刷新 `last_login_at` + 建会话 + 审计）；
2. 身份命中但账号已软删 → **建新账号**并把身份行重指过去（F4：不复活旧账号）；
3. 身份未命中但 `unionid` 命中他人 → 同一个人（另一个应用的 openid）→ 把当前 openid
   挂到他已有账号上，不新建；
4. 都不命中 → `db.withTransaction` 内**同事务**建 `users` + `oauth_identities`
   （拆两段会留下「有账号、无登录方式」的孤儿）；
5. 唯一冲突（并发双标签）→ 重查一次，登录赢家账号；仍拿不到才报错。

### 3.5 前端

- `AuthModal` 在表单与切换标签之间加「或 / 微信扫码登录」（`<a href="/api/auth/wechat/authorize">` 整页跳转），
  `wechatEnabled === false` 时整块不渲染；
- `AuthContext` 挂载时**同步**读走并剥离 `?wechat=ok` / `?wechat_error=`，再 `refreshUser()`
  （同步剥离是 `login_success` 只上报一次的前提：StrictMode 双跑与用户手动刷新都读不到参数了）；
- `UserProfileModal` 按 `email_placeholder` 把邮箱显示为「微信登录（未设邮箱）」、
  按 `has_password === false` 用说明卡替换修改密码表单。

## 6. 风险与已知边界

- **头像 URL 会失效**（官方明说改头像后旧 URL 失效）：一期直存原始 URL，前端降级首字母头像；
  转存 `oss.hao430.cn` 列为后续项。
- **纯微信账号无法设置密码**（旧密码未知、占位邮箱不可达）。
- **不保存 refresh_token** ⇒ 昵称/头像不随微信侧变化刷新。
- **双标签页并发授权**会互相覆盖唯一的 state cookie，先开的那个回调判 `STATE` 失败（重试即可）。
- **管理员恢复已软删的微信账号**会得到无任何登录方式账号（openid 已重指到新账号）。
- 身份键是 per-app 的 `openid`；跨应用同人收敛依赖 `unionid`，一期只有一个 appid，
  该路径只能靠直接预置数据来测。
- PG 真库轮：新表的策略放行**只在双角色轮**（`PG_TEST_URL` 指向受 RLS 约束角色）才有判别力；
  两遍必须各用一个空库。
- **PG 分支另有专门用例**：`tests/pg/oauth-identity.pg.test.ts`（本文件与 `N2` 共用）。
  上面 20 例跑的是内存模式，而生产走的是 PG 分支，所以下面这些只有真库能证明：
  建号 + 建身份**同事务**的原子性（身份行插失败必须回滚掉先插进去的 users 行，否则留下
  「有账号、无任何登录方式」的孤儿）；两条唯一索引的**真实 23505 能否穿透到调用方**
  （而不是被 `handlePgError` 改写成 503 —— 并发收敛全靠它）；`users.email` 是
  **partial** 唯一索引（「目标邮箱属于已注销账号时可绑成功」在内存里只是模拟）；
  以及 `oauth_identities` 的 **RLS `WITH CHECK`** 真的会拒绝「user 作用域下建号 /
  给他人 `user_id` 写身份行」（后者需受限角色，`PG_TEST_URL` 已配却不受约束时**报错而非跳过**）。
