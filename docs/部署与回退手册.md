# ⑤ 验收（见第 6 节清单）
curl -s -o /dev/null -w "%{http_code}\n" https://kg.hao430.cn/

## 1. 拓扑与角色（先搞清楚东西在哪）

| 角色 | 机器 | 位置 / 要点 |
|---|---|---|
| **构建机** | octop-host | 源码 git 仓库 `/home/user/projects/ex-kg`（**唯一源码所在地**） |
| **运行机** | pg-host（8.156.68.107，SSH **1542**） | 站点 `/www/wwwroot/ex-kg/`，**只有 `dist/` + `node_modules/` + `.env` + `package.json`，没有源码、不是 git 仓库** |
| **进程管理** | pg-host 宝塔「Node 项目管理器」（**不是 PM2**） | 启动脚本 `/www/server/nodejs/vhost/scripts/ex_kg.sh`（`www` 用户执行 `node dist/server.cjs`），PID 文件 `/www/server/nodejs/vhost/pids/ex_kg.pid`，日志 `/www/wwwlogs/nodejs/ex_kg.log` |
| **监听** | pg-host | `0.0.0.0:2998`（`server.ts` 里写死 `listen(PORT,'0.0.0.0')`，`.env` 的 `PORT=2998`）；公网入口靠 nginx 反代，不直接对外 |
| **Web 入口** | pg-host nginx | `/www/server/panel/vhost/nginx/node_ex_kg.conf`（宝塔生成）：80→443 跳转，443 反代 `127.0.0.1:2998`；证书 Let's Encrypt（`/etc/letsencrypt/live/kg.hao430.cn/`，`certbot.timer` 自动续期，webroot `/www/wwwroot/acme-challenge`） |
| **数据库** | pg-host 同机 Docker | 容器 `postgres-info-hub`（postgres:16.3），宿主端口 **35432**，库 `arborize`，属主 **`syf_minapp`**；另有运行期角色 `arborize_app`（受 RLS）/ `arborize_system`（`BYPASSRLS`），见 §8.2 |

**四个「不要在服务器上做」的事**：① 不要在 pg-host 上直接改代码（那里没有源码，改了下次部署就丢）；② 不要用 PM2 启停本项目（会与宝塔管理器抢 PID）；③ 不要直接改 `dist/`（会被下次 `rsync --delete` 覆盖）；④ 不要把 owner 连接串（`DATABASE_ADMIN_URL`）写进运行期 `.env` 或留在服务器上——它只属于部署期迁移步骤，进程检测到它即拒绝启动（§8.2 / §11）。

**发布物只有一样**：本地的 `dist/`（前端产物 + `server.cjs` + `migrate.cjs`）。数据库、`.env`、`node_modules`、证书都不在发布物里，回退时也不会被覆盖。

## 2. 环境变量（两套，最容易搞混）

### 2.1 构建期 —— 本地 `/home/user/projects/ex-kg/.env`
**只在 `npm run build` 时生效**，`VITE_` 前缀的变量会被**打进前端产物**（改服务器上的值对本项无效）：

| 变量 | 说明 |
|---|---|
| `VITE_SUPPORT_WECHAT_ID` | **已废弃**（2026-09-10 人工充值入口下架，代码里已移除该变量），留着无害 |
| `VITE_UMAMI_SRC` / `VITE_UMAMI_WEBSITE_ID` | 自托管 Umami 埋点开关，**两项都配才生效**；未配时埋点全 no-op |

### 2.2 运行期 —— 服务端 `/www/wwwroot/ex-kg/.env`（属主 www，权限 644）
`dotenv.config()` 在**进程启动时**读取一次 → **改完必须重启才生效**。

| 变量 | 作用 / 取值 |
|---|---|
| `DATABASE_URL` | **运行期主体**，登录角色 `arborize_app`（DML-only，**受 RLS 约束**）：`postgresql://arborize_app:<pw>@127.0.0.1:35432/arborize`；**缺则直接拒绝启动**（2026-09-16 起真正落地：`checkRuntimeDbRoleInvariants()` 会把「生产未配 DATABASE_URL」当作启动错误——此前只是文档约束，漏配会带着内存模式对外服务，而内存模式只有源码里的演示种子账号）。⚠️ 在把它从属主 `syf_minapp` 翻成 `arborize_app` 之前，RLS 策略**不生效**（属主绕过 `ENABLE` 级 RLS），见 #0014 |
| `DATABASE_SYSTEM_URL` | **跨租户路径**，登录角色 `arborize_system`（DML + `BYPASSRLS`）：按 token 查会话、按 email 查用户、匿名分享、支付宝回调、日清任务、admin 聚合、可观测写入。**生产必须显式配置**——缺省会回落到 `DATABASE_URL`，那些路径随即被 RLS 拦成零行（表现为「所有人登录失效」）；启动时 `checkRuntimeDbRoleInvariants()` 直接拒绝启动 |
| `DATABASE_ADMIN_URL` | **⛔ 不属于运行期 `.env`**。owner（`syf_minapp`）凭据，只由部署期 `npm run migrate` 步骤注入。运行期进程一旦检测到它即拒绝启动（ADR-0019） |
| `NODE_ENV` | 必须 `production`（决定 Secure Cookie、静态资源模式、fail-fast、以及 `checkRuntimeDbRoleInvariants()` 是否生效） |
| `PORT` | `2998`（与 nginx 反代、宝塔项目配置保持一致） |
| `APP_URL` | `https://kg.hao430.cn`。**邮件里的验证/重置链接**与**支付宝 notify_url/return_url** 都由它推导（`{APP_URL}/api/subscriptions/notify`），错一个字母就会静默失效 |
| `SMTP_HOST/PORT/USER/PASS/FROM` | 邮箱验证码/通知；四项缺任一 → 邮件进内存 outbox（干跑），生产等同发不出 |
| `PAYMENT_ENABLED` | 在线支付总开关；`false` → 下单接口一律 `503 PAYMENT_DISABLED`（**当前线上为 false**） |
| `ALIPAY_APP_ID` / `ALIPAY_PRIVATE_KEY` / `ALIPAY_ALIPAY_PUBLIC_KEY` | 三要素齐备 → 走支付宝真实收银台；缺任一 → 回落 mock 渠道（此时 `mock-pay` 自助开通端点才可达——判据是「生效渠道就是 mock」，**不是** `NODE_ENV`：三要素一旦配齐，无论 NODE_ENV 是什么，该端点都返回 404） |
| `ALIPAY_GATEWAY` | 可空（默认 `https://openapi.alipay.com`）；沙箱填 `https://openapi-sandbox.dl.alipaydev.com` |
| `WECHAT_APP_ID` / `WECHAT_APP_SECRET` | 微信开放平台「网站应用」扫码登录（ADR-0022）。**两项都配才启用**；缺任一 → 前端不渲染微信入口（`GET /api/auth/wechat/status` 返回 `enabled:false`），`/authorize` 直接 302 回 `?wechat_error=NOT_CONFIGURED`（绝不半死）。`APP_SECRET` 运行期专用，**不得进前端**（勿加 `VITE_` 前缀）。回调地址由 `APP_URL` 推导为 `{APP_URL}/api/auth/wechat/callback`，**不单设变量**；开放平台后台的「授权回调域」必须登记为 `kg.hao430.cn`（只能填域名，不能带路径），错一个字母即授权失败 |
| `OUTBOUND_ALLOW_PRIVATE_HOSTS` | 出站守卫开关（ADR-0024），默认 `false`。**只影响两件事**：允许把「OpenAI 兼容服务地址」指向回环/内网（如自托管 Ollama `http://localhost:11434/v1`）以及允许明文 `http`。云元数据地址（`169.254.169.254`/`100.100.100.200`/`metadata.*`）**即使设为 true 也仍被拒绝**。线上若用的是公网 provider（dashscope/openai 等），保持 `false` 即可；改成 `true` 等于允许服务端向内网任意主机发起带 Bearer 密钥的请求，请明确知情后再翻 |

> **三个连接串的角色边界（诚实版）**：拿到 `DATABASE_URL` 的攻击者受 RLS 约束、且无 DDL；拿到 `DATABASE_SYSTEM_URL` 的可读全库（仍不能 DDL/DROP）。RLS 的真实价值是**兜住应用层漏写属主过滤的 bug**（返回零行，而不是别人的数据），不是抵御已持有高权限凭据的攻击者。

**⚠️ 密钥两个必查项**（2026-09-10 实测踩过）：
1. **格式**：应用私钥必须是 **PKCS8 单行 base64**（不带 `-----BEGIN` 头尾）。贴成 PKCS1 会报 `ERR_OSSL_UNSUPPORTED`；转换：`openssl pkcs8 -topk8 -nocrypt -in pkcs1.pem -out pkcs8.pem` 后取 body 单行。
2. **不可见字符**：复制粘贴容易夹带 Tab/空格（曾导致 `ALIPAY_APP_ID` 带前导 Tab）。体检：

```bash
# 值长度 + 是否含空白（不打印密钥本体）
awk -F= '/^(ALIPAY_|PAYMENT_ENABLED)/{v=substr($0,index($0,"=")+1);gsub(/"/,"",v);printf "%-26s len=%-5d ws=%s\n",$1,length(v),(v~/[[:space:]]/?"YES":"no")}' .env
# 清理某键的空白
sed -i '/^ALIPAY_APP_ID=/s/[[:space:]]//g' .env
```

## 4. 标准部署流程（每步都带校验）

### Step 0 · 前置检查（本地）
```bash
cd /home/user/projects/ex-kg
git log -1 --format='%h %ci %s'   # 确认要发布的 commit
git status --short                 # 有未提交改动 → 明确知道在发什么
npm run lint                       # tsc --noEmit
npm test                           # 默认套件（内存分支）
# 涉及 PG 路径/SQL/schema 改动时，必须再加真库冒烟（见第 6 节）
```

### Step 1 · 备份线上产物 + 数据库（**铁律**）
快照目录按 `YYYYMMDD_HHMM` 递增，**永不覆盖**；打一份 tar.gz 便于异地保存；**同时 `pg_dump` 生产库**（CD deploy job 已内置，等价命令如下）：

```bash
ssh -p 1542 root@<PG_HOST> 'set -euo pipefail; TS=$(date +%Y%m%d_%H%M); DIR=/www/ex-kg.releases/$TS
  mkdir -p $DIR/db
  cp -a /www/wwwroot/ex-kg/dist $DIR/dist
  cp -a /www/wwwroot/ex-kg/package.json /www/wwwroot/ex-kg/index.html $DIR/
  # 数据库备份（pg-host 同机 Docker；失败/损坏即停，绝不无库备份继续）
  docker exec postgres-info-hub pg_dump -U postgres -d arborize | gzip > $DIR/db/arborize_$TS.sql.gz
  gzip -t $DIR/db/arborize_$TS.sql.gz && test -s $DIR/db/arborize_$TS.sql.gz
  ( cd /www/ex-kg.releases && tar czf $TS.tar.gz $TS/dist $TS/db )
  cat > $DIR/RELEASE_INFO.txt <<EOF
【ex-kg 回退快照】
备份时间(北京): $(date "+%Y-%m-%d %H:%M:%S")
对应线上构建: $(ls /www/wwwroot/ex-kg/dist/assets | grep -E "^index-.*\.js$")
对应源码 commit: <填本次线上对应的 commit>
支付开关: $(grep -m1 ^PAYMENT_ENABLED /www/wwwroot/ex-kg/.env)
数据库备份: db/arborize_$TS.sql.gz
--- 代码回退方法 ---
1) rm -rf /www/wwwroot/ex-kg/dist && cp -a $DIR/dist /www/wwwroot/ex-kg/dist
2) chown -R www:www /www/wwwroot/ex-kg/dist
3) kill \$(cat /www/server/nodejs/vhost/pids/ex_kg.pid)
4) su www -s /bin/bash -c "bash /www/server/nodejs/vhost/scripts/ex_kg.sh"
--- 数据库恢复方法（破坏性变更后人工执行，先停写）---
gunzip -c $DIR/db/arborize_$TS.sql.gz | docker exec -i postgres-info-hub psql -U postgres -d arborize
EOF
  # 保留最近 5 份（目录 + tar.gz 同步清理，DB 备份随目录轮转）
  for old in $(find /www/ex-kg.releases -maxdepth 1 -mindepth 1 -type d -printf "%f\n" | grep -E "^[0-9]{8}_[0-9]{4}$" | sort -r | tail -n +6); do
    rm -rf "/www/ex-kg.releases/$old" "/www/ex-kg.releases/$old.tar.gz"
  done
  echo "SNAPSHOT=$DIR"'

# 再拉一份到构建机做异地保险
scp -P 1542 root@<PG_HOST>:/www/ex-kg.releases/<TS>.tar.gz ./backups/
```

> 回退**代码**用快照目录（§5 / CD rollback job）；**数据库不回滚**——快照里的 `db/*.sql.gz` 仅用于破坏性变更后的人工恢复，自动回退不会动库（避免丢掉快照之后写入的数据）。

### Step 2 · 构建
```bash
npm run build
# = vite build（前端 → dist/，含 assets/ 与 KaTeX 字体）
# + esbuild server.ts → dist/server.cjs（.map 一并产出）
# + esbuild server/core/migrate-cli.ts → dist/migrate.cjs（ADR-0019 的部署期迁移入口）
```

### Step 3 · 产物校验（3 秒，能挡住 80% 的低级事故）
```bash
ls dist/                                            # assets index.html logo server.cjs server.cjs.map migrate.cjs
ls dist/assets | grep -E 'index-.*\.(js|css)$'      # 新 hash（前端有改动时必然变化）
ls dist/assets | grep -c KaTeX                      # 必须是 59（KaTeX 字体，被 index-*.css 的 @font-face 引用）
grep -c 'alipay.trade.page.pay' dist/server.cjs     # 后端特性抽查（示例）
grep -c 'verified and initialized' dist/migrate.cjs # 迁移成功标志必须编进迁移产物（CD 靠它判定）
```
**发布物必须自洽**：`index.html` 引用的 `index-*.js/css` 必须在 `assets/` 里，且 CSS 依赖的 KaTeX 字体齐全——三者缺一，线上就是白屏或公式 404。

### Step 4 · 同步到线上
```bash
# 常规（会删除线上旧 hash 资产，保持 dist 与本地完全一致）
rsync -az --delete -e "ssh -p 1542" dist/ root@<PG_HOST>:/www/wwwroot/ex-kg/dist/
ssh -p 1542 root@<PG_HOST> 'chown -R www:www /www/wwwroot/ex-kg/dist'
```
- `--delete` 是**安全**的：本地 `dist/` 是完整镜像（KaTeX 字体也在其中），线上不需要任何「本地没有的文件」。
- **例外**：如果本次只推文件、**暂不重启**（例如要先让用户填 `.env`），请**去掉 `--delete`**——保留旧 hash 资源，避免浏览器里缓存了旧 `index.html` 的访客请求旧 js 得到 404；等重启那次再带 `--delete` 清理。

### Step 4.5 · 部署期迁移（ADR-0019，**必须在重启之前**）

生产进程**零 DDL 权限**，schema 由这一步以 owner 角色执行。**迁移失败即中止发布且不重启**——旧进程继续服务，而不是起一个半 schema 的新进程。

```bash
# ① owner 凭据经 ssh stdin 落到远端 mode-600 临时文件（不进 argv，远端 ps 看不到）
printf 'DATABASE_ADMIN_URL=%s\n' '<owner 连接串>' | \
  ssh -p 1542 root@<PG_HOST> 'umask 077 && cat > /www/wwwroot/ex-kg/.migrate.env'

# ② 跑迁移，无论成败都先删凭据文件
ssh -p 1542 root@<PG_HOST> 'set -e; cd /www/wwwroot/ex-kg
  trap "rm -f /www/wwwroot/ex-kg/.migrate.env" EXIT
  set -a; . /www/wwwroot/ex-kg/.migrate.env; set +a
  export NODE_ENV=production          # 生产必须显式给 owner 串，不对 DATABASE_URL 回落
  OUT=$(/www/server/nodejs/v22.22.2/bin/node dist/migrate.cjs 2>&1) || { echo "$OUT"; echo "❌ 迁移失败"; exit 1; }
  echo "$OUT" | grep -q "verified and initialized" || { echo "❌ 迁移未打印成功标志（静默失败）"; exit 1; }
  echo "schema ok"'
```

- ⛔ **不要把 `DATABASE_ADMIN_URL` 写进 `/www/wwwroot/ex-kg/.env`**：运行期进程一旦检测到它即拒绝启动（那是刻意的最强档位）。CD 的 migrate 步骤用的是同一套「即用即删」写法。
- 迁移做的是**幂等增量**：建表/加列/加索引、RLS 策略（`ENABLE ROW LEVEL SECURITY` + `tenant_isolation`）、归属探针 `canvas_probe`。
- 本地开发用 `npm run migrate:dev`（允许回落 `DATABASE_URL`；受限角色跑 DDL 会失败，属预期）。

### Step 5 · 重启进程
```bash

  PID=$(cat /www/server/nodejs/vhost/pids/ex_kg.pid)
  kill $PID; for i in $(seq 1 40); do kill -0 $PID 2>/dev/null || break; sleep 0.5; done
  kill -0 $PID 2>/dev/null && kill -9 $PID
  su www -s /bin/bash -c "bash /www/server/nodejs/vhost/scripts/ex_kg.sh"
  sleep 4; echo "new PID=$(cat /www/server/nodejs/vhost/pids/ex_kg.pid)"
  tail -4 /www/wwwlogs/nodejs/ex_kg.log'
```
启动日志正常长相（缺一行就说明有问题）：
```

Arborize (枝想) enterprise server listening on http://0.0.0.0:2998
```
> **生产启动日志里不再有 schema 行**（`✅ PostgreSQL schema & users verified and initialized.`）——迁移已上移到 Step 4.5，生产进程零 DDL。该行现在只在 Step 4.5 的迁移输出里出现，不要在启动日志里 grep 它（早先的门就是那么做的，已失效）。

### 5.1 数据库角色分离与 RLS（ADR-0019）的回退

**最快的回退是翻连接串，不是回滚产物**：RLS 的风险面集中在「app 角色看得见的行变少」，把主体换回属主即可一分钟内恢复，无需动 dist、不动数据。

```bash
# ① 首选：把运行期主体换回属主（秒级；策略留在库里，对属主不生效）
ssh -p 1542 root@<PG_HOST> "sed -i 's#^DATABASE_URL=.*#DATABASE_URL=\"postgresql://syf_minapp:<pw>@127.0.0.1:35432/arborize\"#' /www/wwwroot/ex-kg/.env"
# ② 重启（同 Step 5）后确认 /api/health 与登录/画布读写恢复正常
```

- **属主主体下行为与改造前完全一致**（`ENABLE ROW LEVEL SECURITY` 对属主无效），所以这一步是安全的止血阀，不是「绕过安全」——它只是回到改造前的权限模型。
- ⛔ **回滚到 ADR-0019 之前的 dist（不认识 `getDb()`/作用域）时，`DATABASE_URL` 必须同时是 owner**：旧构建直接读 `DATABASE_URL` 并 `pool.query`，没有 `app.user_id` 作用域。若此时 `DATABASE_URL` 还指向 `arborize_app`，旧构建的每条查询都会以「无作用域」执行，被 RLS 拦成零行——表现为「登录不上、画板全空」，且**不报错**（正是最需要警惕的静默模式）。
- ⛔ **不要用回滚来「关掉 RLS」**：策略与 `ENABLE` 留在库里是**幂等且无害**的（owner 主体下不生效）；删策略/关 `ENABLE` 属于 DDL 变更，需要走 migrate，不该混在故障处置里。
- ⛔ **永远不要给这些表加 `FORCE ROW LEVEL SECURITY`**（回退时若要「加强」RLS 也不许）：它会让属主也受策略约束，`canvas_probe`（`SECURITY DEFINER`）随即失效，「他人的画板」从 403 静默退化成 404。
- **角色创建本身不可逆但无害**（纯增量）：回退不需要删 `arborize_app` / `arborize_system`，留着即可，下次发布还用得上。

### 5.2 画布同步重构（ADR-0017 / ADR-0018）的发布顺序与回滚副作用

画布保存从「整板替换」改成「节点级合并」、默认画板从「全局共享」改成「私有」，两者都有**顺序要求**和**不可逆点**。乱序回滚会静默毁数据，本节是硬约束。

**发布顺序（不可交换）**

1. 服务端 DDL + 双路径代码（`SAVE_DEFAULT_BOARD_MODE=legacy`、`SAVE_LEGACY_REPLACE_ENABLED` 未设）→ 部署。此步**零行为变化**：新旧客户端都正常。
2. 确认 CI 的 schema 日志门 greps 到 `schema & verified and initialized.`（`ci.yml`）。
3. 客户端切发 `protocolVersion: 2`（新 diff 协议）→ 部署 dist。
4. **soak ≥7 天**：观察 `[canvas-save]` 的 `mode=replace` 是否归零、`ignored=`/`repaired=` 是否异常。
5. 归零后：先 `pg_dump`，再翻 `SAVE_LEGACY_REPLACE_ENABLED=false`。
6. 再 `pg_dump`，再翻 `SAVE_DEFAULT_BOARD_MODE=private`（客户端第 3 步已先行）。

**回滚副作用（逐条都是「代码能跑但语义错」或「数据消失」，不是崩溃）**

- ⛔ **绝不能把服务端产物回滚到阶段 3 之前的版本**（不认识 `protocolVersion` 的构建）。旧代码把 `nodes` 当整板：`DELETE FROM nodes WHERE canvas_id=$1` 后重插 payload。而新客户端只发**本次改动**的节点，于是「设备没碰过的节点」会被当成「被删了」**全量清掉**——一次保存即可毁掉整块画板。要回滚服务端，最远只能回到「双路径共存」的那一版，并同时把 `SAVE_LEGACY_REPLACE_ENABLED` 恢复为未设/`true`。
- ⛔ **翻 `private` 之后不能回滚客户端 dist 到阶段 5b 之前**。老客户端硬编码 `default-board`，在 private 模式下非属主保存会 403，用户表现为「改了存不上」。
- **代码回滚到「读路径没有 `deleted_at IS NULL` 过滤」的版本**：墓碑行会被当作活节点/活边读出来，用户看到已删内容复活。回滚前先清墓碑行（边先于节点，顺序别反）：
  ```sql
  DELETE FROM edges WHERE deleted_at IS NOT NULL;
  DELETE FROM nodes WHERE deleted_at IS NOT NULL;
  ```
  或直接恢复当日 `pg_dump`。另注意 `idx_nodes_canvas_id`/`idx_edges_canvas_id` 已是 partial（`WHERE deleted_at IS NULL`），不带该过滤的旧查询用不上它们，会退化为顺序扫描（慢，但不错）。
- **`SAVE_DEFAULT_BOARD_MODE` 翻回 `legacy`**：私有默认板里的内容会「消失」——读写目标换回那一行共享板。翻之前必须有当日 `pg_dump`。
- **`SAVE_LEGACY_REPLACE_ENABLED` 翻回 `true`**：一旦有用户用新语义（「没带 = 不动」）写入过，翻回旧语义会让新客户端整板 payload 里没带的节点被删。翻之前必须有当日 `pg_dump`。
- **墓碑 GC 不可逆**：`CANVAS_TOMBSTONE_RETENTION_DAYS` 回收掉的墓碑无法恢复，超过保留期未联网的设备会把旧节点重传为新节点（内容是该用户自己的）。生产**不要**把该值设为 `0`（等于每次 GC 全清墓碑）。
- 恢复手段只有 `pg_dump`：没有 schema 版本表，旧语义一旦停止，数据层面无法靠代码回滚还原。

> 翻开关前后的验收口径：`[canvas-save] canvas=<id> mode=merge protocolVersion=2 bytes=<n> ops={...} ignored=<n> repaired=<n>`（只记计数与画板 id，节点内容不进日志）。`bytes` 应显著低于同期的整板 payload；`repaired` 常态应为 0，持续非 0 说明客户端 diff 丢了父节点。

## 7. 故障排查手册（本次上线踩坑沉淀）

| 症状 | 根因 | 处理 |
|---|---|---|
| 下单/结算接口 503 `DB_UNAVAILABLE`，日志里**没有真因** | ① `CASE WHEN $6='paid'` 把同一占位符用在两种类型上下文 → PG `42P08 inconsistent types deduced`；② 生产 fail-fast 先抛 503，仓储 catch 里的 `console.warn` 永远执行不到 | ① 同一参数改用**独立占位符**（`::text` 强转无效）；② `handlePgError` 内部先 `console.error` 再抛（已修） |
| 支付宝 `payUrl` 里 `notify_url=http://localhost:3000` | 模块级 `const APP_URL = process.env.APP_URL \|\| 'http://localhost:3000'` 在 `dotenv.config()`（在 `server.ts` 里）**之前**求值 | 改**惰性函数** `getAppUrl()`；同一类坑还有 `mailer` 的 dry-run、`memory-store` 的 `EVENT_LOGS_MAX`。**凡模块级读 `process.env` 都要警惕** |
| 空库部署后「表全都不存在」，启动日志只有一条被吞的错 | `CREATE EXTENSION pgcrypto` 在事务里失败（非超级用户 → `42501`），裸 `try/catch` 吞掉，但事务已 aborted → 后续 DDL 全 `25P02`，整批回滚 | 用 `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` 包住（已修，仅 warn 并继续） |
| 新库 `initDbSchema` 报 `42501 permission denied for schema public` | PG15+ 起 `public` schema 不再默认给非属主 CREATE 权限 | 建库时指定属主：`CREATE DATABASE arborize OWNER <应用角色>;` |
| 保存画布 500：`edges_source_id_fkey` / `nodes_pkey` 违反 | 前端残留「已删除节点的边」；或同一 payload 内节点 id 重复（生产日志曾出现 48 次） | 服务端自愈：丢弃端点缺失的边 + 按 id 去重 + `console.warn`（已修）。**注意**：跨画布 id 复用仍会撞 `nodes_pkey`，需前端克隆时重生成 id |
| 重启后 `Cannot find module 'xxx'` | esbuild `--packages=external`，新依赖没在服务端装 | 第 3 节补装；发布前跑依赖预检 |

| 铺天盖地 500 `DB_SCOPE_MISSING`（日志 `[db-guard] 请求作用域缺失`） | 代码路径没建立数据库作用域就查库（`getDb()` 的刻意响亮失败，**不是**数据库故障） | 在该路径入口包 `runWithUser(userId, …)` 或 `runWithSystem('理由', …)`；不要把 `DB_SCOPE_MISSING` 当成 `DB_UNAVAILABLE` 去查 PG |
| 日志 `[db-guard] RLS 策略拒绝了本次查询——应用层漏写了属主过滤`（SQLSTATE `42501` + `row-level security policy`） | 应用层某条 SQL 在 app 角色下写了别人的 `user_id` / 漏了属主条件，被 `WITH CHECK` 拦住 | **这是代码 bug**：补属主过滤或改走 system 作用域。别去放宽策略 |
| 所有人「登录失效」、画板列表全空，但**没有任何报错** | `DATABASE_SYSTEM_URL` 缺失 → system 池回落到 app 角色 → 按 token 查会话等跨租户路径被 RLS 拦成零行 | 补 `DATABASE_SYSTEM_URL` 并重启；`checkRuntimeDbRoleInvariants()` 本应在启动时拒绝这种配置，若进程起来了说明 `NODE_ENV !== 'production'` |
| 重启后进程起不来，日志提到 `DATABASE_ADMIN_URL` | owner 凭据被写进了运行期 `.env` —— 启动断言刻意拒绝（最坏情况是应用进程持 DDL 权限，RLS 意义全无） | 从 `/www/wwwroot/ex-kg/.env` 删掉该键（它只属于 Step 4.5 的临时 env 文件），再重启 |
| 迁移报 `42501 permission denied` / DDL 失败 | 迁移用了受限角色（`DATABASE_ADMIN_URL` 没注入，或 `NODE_ENV` 不是 `production` 导致回落 `DATABASE_URL`） | 按 Step 4.5 显式提供 owner 串；**这是期望行为**——宁可迁移报错，也不要半个 schema |
| 他人画板的「保存」从 403 变成 404 | `canvas_probe` 失效：有人给表加了 `FORCE ROW LEVEL SECURITY`（属主也受策略约束，探针看不见他人行） | 立刻 `ALTER TABLE … NO FORCE ROW LEVEL SECURITY`；两条守护线（arch-test + 真库 `relforcerowsecurity` 断言）本应挡住它 |
| 重启后进程起不来，日志 `❌ 生产环境未配置 DATABASE_URL` | 安全审查 M2 的启动断言：生产环境漏配连接串，会带着内存模式对外服务，而内存模式只有源码里的演示种子账号（公开口令） | 在 `/www/wwwroot/ex-kg/.env` 补上 `DATABASE_URL`（与必要的 `DATABASE_SYSTEM_URL`）后重启。**不要**为了让进程起来而临时把 `NODE_ENV` 改成非 production |
| 运营台保存/联调模型配置报 `OUTBOUND_URL_REJECTED` | ADR-0024 出站守卫：地址是内网/回环（如 Ollama `http://localhost:11434/v1`）、或明文 `http`、或指向云元数据 | 公网 provider 改用 `https://`；确实要连内网自托管模型时在 `.env` 设 `OUTBOUND_ALLOW_PRIVATE_HOSTS=true` 并重启（云元数据地址即使开了也仍被拒） |
| 联调模型报 `API_KEY_REQUIRED_FOR_NEW_HOST` | ADR-0024：改了服务地址但没填 Key，此时回落已保存的密钥等于把平台密钥送往新主机，故刻意拒绝 | 换地址时把新渠道的 Key 一并填上并保存；测已保存的那台则不用重填 |
| 页面样式/公式正常但浏览器 Console 报 CSP 拦截、或某段脚本不执行 | 生产启用了 CSP（`script-src 'self'`），而新增了内联 `<script>`（安全审查 M5） | 把内联脚本外置到 `public/*.js`（index.html 里只允许 `<script src>`），重新 `npm run build` 发布；**不要**为省事去开 `'unsafe-inline'` |
| 邮件里的重置/验证链接指向了奇怪域名 | 有代码绕过了 `server/lib/origin.ts`，直接用 `${req.protocol}://${req.get('host')}` 拼链接（Host 头是请求方可控的） | 改用 `resolveRequestOrigin(req)`；同时确认 `APP_URL` 已配置（配了它才完全不看 Host） |

## 8. 数据库与 schema 注意事项

### 8.1 谁在什么时候改 schema（ADR-0019）

- **生产进程零 DDL 权限**：`initDbSchema()` 不再从请求路径或服务启动时执行，改由**部署期 migrate 步骤**（Step 4.5 / CD 的 migrate step）以 owner 角色跑一次。因此 **`npm run build` 会同时产出 `dist/migrate.cjs`，它必须与 `dist/server.cjs` 一起同步上线**——只推 server.cjs 会让 schema 变更悄悄不生效。
- **懒迁移调用已全部摘除**（含 `log-cleanup`、`db-status`）：`server/repositories/**` 不得再出现 `initDbSchema(`，由 `arch-tests/db-scope-discipline.test.mjs` 锁定。**非生产**（`NODE_ENV !== 'production'`）仍保留启动兜底，供 `npm run dev` 与本地 PG 冒烟使用。
- **迁移失败不再静默**：migrate 进程退出码非 0 或没打印 `✅ PostgreSQL schema & users verified and initialized.` 都会让 CD **中止发布且不重启**——旧进程继续服务，而不是起一个半 schema 的新进程。这修掉了早先「`initDbSchema` 出错只打日志、不阻断监听，验收照过」的静默面。
- `initDbSchema()` 仍是 schema 的**唯一事实源**（不引入迁移框架），对存量库做**幂等增量迁移**。⚠️ 它并非"只补列不删列"——源码中已含 `DROP COLUMN`/`DROP TABLE`（点数体系清理）、`UPDATE ... SET`（自指脏数据清洗）、`ALTER COLUMN SET DEFAULT` 等语句，迁移时同样会改动生产库。改列类型/重命名列/大表回填仍需人工 `ALTER`。
- **数据库备份**：CD deploy 在备份步骤自动 `pg_dump` 到快照 `db/arborize_<TS>.sql.gz`（失败/损坏即中止发布）；服务端 `/www/ex-kg.releases/` 的**目录与 tar.gz 只保留最近 5 份**（DB 备份随目录轮转，**构建机 `backups/` 的手工异地副本不受 workflow 管理，需自行清理**）。破坏性变更前先确认快照含 DB 备份再发布；恢复用快照 `RELEASE_INFO.txt` 里的命令（会覆盖当前库，先停写）。

### 8.2 三个角色与授权（ADR-0019）

| 角色 | 权限 | 谁在用 |
|---|---|---|
| `syf_minapp`（属主） | 全部 + DDL，**绕过** `ENABLE` 级 RLS | 仅部署期 migrate |
| `arborize_system` | DML + `BYPASSRLS` | 跨租户路径（会话/登录/匿名分享/支付宝回调/日清/admin/可观测写入） |
| `arborize_app` | DML-only，**受 RLS** | 运行期主体（翻 `DATABASE_URL` 之后） |

**建角色（一次性，需超级用户）**——注意顺序：**授权必须发生在表已建出来之后**；`ALTER DEFAULT PRIVILEGES` 反过来要**尽早设**，否则之后迁移新建的表不自动授权、app 角色看起来「表不存在」：

```bash
docker exec -i postgres-info-hub psql -U postgres -d arborize -v ON_ERROR_STOP=1 <<'SQL'
CREATE ROLE arborize_app    LOGIN PASSWORD '<强口令>';
CREATE ROLE arborize_system LOGIN PASSWORD '<强口令>';
-- BYPASSRLS 需超级用户。若拿不到超级用户，退路是把 arborize_system 设为表属主
-- （属主天然绕过 ENABLE 级 RLS），并把 syf_minapp 降为普通角色——届时同步修订 ADR-0019。
ALTER ROLE arborize_system BYPASSRLS;

GRANT USAGE ON SCHEMA public TO arborize_app, arborize_system;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES    IN SCHEMA public TO arborize_app, arborize_system;
GRANT USAGE, SELECT                  ON ALL SEQUENCES IN SCHEMA public TO arborize_app, arborize_system;

-- 之后由 syf_minapp 执行的迁移新建的表/序列自动继承授权
ALTER DEFAULT PRIVILEGES FOR ROLE syf_minapp IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO arborize_app, arborize_system;
ALTER DEFAULT PRIVILEGES FOR ROLE syf_minapp IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO arborize_app, arborize_system;
SQL
```

- 建完角色**跑一次 migrate**：它会给 15 张表 `ENABLE ROW LEVEL SECURITY` + `tenant_isolation` 策略，并建归属探针 `canvas_probe`（`SECURITY DEFINER`，已收回 PUBLIC 的执行权、按需授给 app/system）。
- **验证授权是否真的到位**（比 `\dp` 更贴近实际）：以 app 角色连一次，`SELECT row_security_active('canvases')` 应为 `true`——这正是 CI 第二遍 PG 冒烟的前置断言。
- ⛔ **`FORCE ROW LEVEL SECURITY` 永不可加**：它让属主也受策略约束 → `canvas_probe` 看不见他人行 → 他人画板的 403 静默退化成 404。

### 8.3 库、属主与历史人工变更

- **生产库现状属主是 `syf_minapp`**，`arborize` 库已包含全部表与 3 个种子账号（`admin@/user@/vip@deepdive.ai`，`user@` 已被冻结）。
- **新建/重建库正确姿势**（迁移或灾难恢复时）：
  ```bash
  docker exec postgres-info-hub psql -U postgres -c "CREATE DATABASE arborize OWNER syf_minapp;"
  # 然后跑一次 npm run migrate（以 owner）建表；属主不对会 42501（见第 7 节）
  ```
- **历史人工变更**（源码 DDL 未反映，重建库要补）：
  - `canvases/nodes/edges/canvas_shares/canvas_snapshots/canvas_tags/node_attachments/ai_request_logs/user_audit_logs` 的 `id`/`canvas_id`/`node_id`/`parent_id`/`source_id`/`target_id` 列由 `varchar(64)` 扩到 **`varchar(255)`**（源码 `CREATE TABLE` 仍是 64）；
  - 追加列：`canvases.default_model`、`nodes.model_used`、`edges.source_handle`、`edges.target_handle`。
- **PG 冒烟必须用空库**：`tests/pg/pg-smoke.test.ts` 注册固定邮箱 `j3-*@test.local`（`admin-count`/`canvas-normalize` 同理 `p-pg-*`），复用旧库会撞 `EMAIL_EXISTS`(409) 与验证码 **60s 冷却**而误报失败——失败信息还指向「没发出验证码邮件」，真因在夹具。官方 compose（`docker-compose.pg-smoke.yml`）用 tmpfs，容器即抛，天然满足。**CI 的两遍冒烟因此各用一个库**：第一遍 `arborize_test`、第二遍（受 RLS）`arborize_rls_test`。跑完记得 `DROP DATABASE`。
- **库级授权要按库做**：角色（`arborize_app`/`arborize_system`）是集群级的，但 `GRANT ... ON ALL TABLES` 与 `ALTER DEFAULT PRIVILEGES` 都是**按库**存储的——新开一个冒烟库就得重新授权，否则 app 角色表现为「表不存在」。
- **`tests/pg/` 6 个文件共用同一个库**，各自在 `before()` 里跑一遍迁移（DDL 取 `ACCESS EXCLUSIVE` 锁），故 CI 用 `--test-concurrency=1` 串行跑——并行只会互相等锁，首轮还可能因回落池的 5s 语句超时把迁移打成 `false`，那是排障噪声而非被测行为。

### 8.4 RLS 上线顺序（**不可交换**，#0014 的生效前提）

| 步 | 动作 | 这一步之后的行为 |
|---|---|---|
| 1 | 代码合入并发布（策略/角色/作用域代码就位） | **零变化**：`DATABASE_URL` 仍是 owner，RLS 对它不生效 |
| 2 | 建 `arborize_app` / `arborize_system` + 授权（§8.2） | 无变化（纯增量） |
| 3 | 运行期 `.env` 加 `DATABASE_SYSTEM_URL` → 重启 | 无变化（system 路径仍以 owner 执行） |
| 4 | 配 Secret `DATABASE_ADMIN_URL`（§11 前置 3） | 无变化（只在 deploy 的迁移步骤用） |
| 5 | 发一次版（走 migrate：建策略 + `ENABLE ROW LEVEL SECURITY`） | **仍无变化**：owner 主体绕过 RLS |
| 6 | 把 `DATABASE_URL` 翻成 `arborize_app` → 重启 | ⚠️ **RLS 此刻才生效**。缺 `DATABASE_SYSTEM_URL` 会拒绝启动（响亮，不静默降级） |
| 7 | 观测 `/api/db/status` 无 `degraded`、日志无 `DB_SCOPE_MISSING` / `42501` | 稳定则收工 |

- 第 1–5 步全部「零行为变化」是刻意的：**先让基础设施就位，最后才动权限开关**，出问题时只需回退一个环境变量（§5.1）。
- 第 6 步之后若出现异常，第一动作是 §5.1 的「换回 owner 串 + 重启」，而不是排查代码——秒级止血，然后离线分析。
- **执行状态（2026-09-12）：第 2–7 步已在 pg-host 执行完毕，生产库 RLS 已实际生效。** 实测回执（角色属性、`pg_default_acl`、`relrowsecurity` 15 行 / `FORCE` 0 行、运行期连接为 `arborize_app`、端到端登录与画板读写全 200、跨租户 404/403）逐项记在 `docs/技术债清单.md` #0014 的「生效前提」清单里。

## 11. CD（GitHub Actions 自动发布与回退）

> Workflow：`.github/workflows/ci.yml`（名称 CI/CD）。**前置配置（一次性）**：
> 1. pg-host `/root/.ssh/authorized_keys` 追加部署公钥（ed25519 `github-actions-deploy-ex-kg`，2026-09-10 生成）；
> 2. 仓库 Settings → Secrets → Actions：`DEPLOY_HOST` / `DEPLOY_PORT` / `DEPLOY_USER` / `DEPLOY_SSH_KEY`（私钥全文）；
> 3. **`DATABASE_ADMIN_URL`**（ADR-0019）：owner（`syf_minapp`）连接串，**仅由 deploy job 的「部署期迁移」步骤注入**——经 ssh **stdin** 落到远端 mode-600 临时文件、用后即删，不进运行期 `.env`，也不出现在远端 `ps` 里。缺它则 deploy 直接失败（不静默跳过迁移）。
> 4. 一次性建好 `arborize_app` / `arborize_system` 两个角色并授权（见 §8.2）——**CI 的 PG 冒烟第二遍与生产翻开关都依赖它们**。
>
> 注：私有仓库 Free 套餐不支持 Environment「Required reviewers」审批，**发版人工放行 = 手动 Run workflow**（push 不会自动发版）；后续升级 Pro 或仓库转公开可改回自动部署 + 审批。

### 11.1 发布链路

```
push main
  → ci job（自动门禁）：npm ci → tsc → 全量测试（内存）→ arch-tests → build
    → PG 冒烟第一遍（owner 单角色，覆盖既有行为）
    → 建 app/system 角色并授权（表已由第一遍建出，授权必须在其后）
    → PG 冒烟第二遍（PG_TEST_URL=arborize_app + DATABASE_SYSTEM_URL=arborize_system）
        └ 唯一能证明「每个 PG 路径都带上了作用域、每条策略都放行得通」的检验
    → 上传 dist 构建物

发版（Actions → CI/CD → Run workflow，rollback_snapshot 留空 → deploy job）：
  下载 CI 构建物 → 备份快照（RELEASE_INFO.txt 含 commit SHA；含 pg_dump）
  → rsync package*.json → rsync dist/ --delete → 服务端 npm install --omit=dev + 依赖预检（缺模块即停，不重启）
  → **部署期迁移**（owner 凭据 stdin 注入 + 即用即删；失败即中止，不重启；须见
     "verified and initialized" 成功标志）
  → 重启（日志须见 listening 行；**不得**出现 DATABASE_ADMIN_URL）
  → 验收：/api/health + 首页 200 + 新 index-*.js 200
```

- **发布物 = CI 测试通过的构建物**（artifact 传递，不经本地二次构建）。
- **迁移在重启之前**：顺序反了会起一个半 schema 的新进程；迁移失败时旧进程继续服务（手工流程见 Step 4.5）。
- **失败即停**：任一步红则 job 红，不做自动回退（避免验收抖动误判）；回退走 11.2 人工判断。
- `concurrency: deploy-production` 串行化部署，中途不可取消。
- 纯回退触发（`rollback_snapshot` 非空）**不跑 ci job**：快照是已验收产物，无需再验。

### 11.2 一键回退

Actions → CI/CD → Run workflow → `rollback_snapshot` 填快照目录名（如 `20260910_1447`）→ Run。
执行：格式校验（`YYYYMMDD_HHMM`，防注入）→ 快照存在性预检 → 快照 dist 覆盖 → 重启 → health/首页验收。
等价于第 5 节手工命令；快照列表 SSH 上 `ls /www/ex-kg.releases/` 查看。

### 11.3 与人工流程的分工

| 场景 | 用哪条路 |
|---|---|
| 日常发版 | Actions 手动 Run workflow（发版前确认 CI 最近一次全绿） |
| CI/Actions 故障、需紧急带外发布 | 第 4 节人工流程（构建机本地 build + rsync） |
| 线上故障回退 | 11.2 一键回退（或 §5 手工） |
| 只改 `.env` / 支付开关 | 第 2/9 节（登服务器改 + 重启，与 CD 无关） |
